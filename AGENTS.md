# PGMaps Agent Instructions

## CI workflows

- Only `checks.yml` (typecheck, lint, format, unit tests) and `deploy.yml` (Pages build; deploys on `main`) run automatically.
- Feature-specific browser or reference suites (forest drought, forestry roads, roads vs native R, MMGIS, Nechako, viewshed and any new one) are `workflow_dispatch` only. Do not add `pull_request` or `push` triggers to them; run them by hand (Actions → Run workflow, choosing the PR branch) when a change needs that evidence.

## Scraper-owned data

- `vendor/bcdatamapper` is the Git submodule and source of truth for scraper code, source archives, and deployable scraper snapshots.
- Treat paths copied by `scripts/sync-bcdatamapper-data.mjs` into `public/data` as generated build output. Do not force-add ignored copies of those files to the PGMaps repository.
- In particular, WARS artifacts belong only in `vendor/bcdatamapper/datascrapers/bc/wars/output`. Keep the manifest and deterministic compressed `*.gz` snapshots there; generate `public/data/wars` with `npm run data:sync-from-bcdatamapper`.
- Keep deployment checkout configured with recursive submodules. A build that does not initialize `vendor/bcdatamapper` cannot assemble scraper-owned data.
- `vendor/canadadatamapper` holds national (Canada-wide) scrapers under the same rules; `scripts/sync-bcdatamapper-data.mjs` copies its `canadaPathMappings` too, and the deploy cache key includes both submodule revisions. ISED cell sites land at `public/data/canada/cell-sites`. Build towers from ISED's `Site_Data_Extract_FX.zip`, never by scraping ertyu.org, whose `robots.txt` disallows automated clients.

## Data hosts

- `docs/data-hosts.md` is the contract for `src/config/data-hosts.json`, which lists the `public/data` folders served from another host. Moving a folder off Pages is one entry there; the sync script, deploy cache key and service worker follow it.
- `cciss`, `census`, `citypg`, `drought`, `forest` and `network-availability` are served by bcdatamapper's own Pages site, not this build. Their layout lives in `vendor/bcdatamapper/pages/site.json`; do not re-add their mappings to `scripts/sync-bcdatamapper-data.mjs`. A bcdatamapper data push reaches the live app without a deploy, and `scripts/check-data-hosts.mjs` warns in the deploy when the live folders differ from the pinned submodule.
- Those folders are not in `public/data` during a build or a unit run. A build script that needs one reads it through `createDataSourceResolver` (`scripts/lib/data-source-path.mjs`), and a test reads the submodule's copy. The deploy only copies what bcdatamapper commits, already built: do not add a step that builds scraper output into `public/data`.
- bcdatamapper's Pages site is 541 MB of its 1 GB limit. Publish only what the app loads: `canada-admin` (202 MB) sat there unread until it was removed, because the story reads PMTiles on R2. Check for a reference in `src` before adding a folder, and leave full-detail sources (the `BCMoH` originals, province-wide `BCFWA` files) out.
- Resolve every data URL with `withBase` (`src/lib/dataUrl.ts`), directly or through `fetchJson`/`fetchBytes`. A bare `'/data/...'` handed to MapLibre, deck.gl, a worker or a link, or a URL built from `import.meta.env.BASE_URL`, always loads from this site and breaks once its folder moves.

## LiDAR point cloud tiles

- `vendor/pgmaps-lidar-data` builds and publishes the EPT tiles. Its Release stores them and its own Pages site serves them to the browser; PGMaps loads them at runtime and does not deploy them. Do not bring them back into `dist`: at 495 MB they put this site over GitHub's 1 GB Pages limit, which `deploy.yml` now warns about at 900 MB compressed.
- Browsers cannot read a GitHub Release asset, because GitHub sends no CORS headers on those downloads. A Release can store data but cannot serve it to the app.
- Pages keys a deployment by commit, and a cancelled commit cannot deploy again. Retry a timed-out deploy with a new commit, not a rerun.
- Import & data reads a LAS/LAZ too large to load whole one chunk at a time (`largeLaz*.ts`): `src/lib/lidar/lazChunkTable.ts` decodes LAZ's chunk table, a port of LASzip (Apache-2.0, `NOTICE-LASZIP.md`), and laz-perf's `ChunkDecoder` decodes each chunk in a worker. Never read such a file with `arrayBuffer()` or laz-perf's whole-file `LASZip`: a LidarBC tile is up to 2.8 GB and 3–5 GB unpacked, past WebAssembly's 4 GB. Keep `lazChunkTable.ts`, `largeLaz.ts` and `largeLazDecode.ts` free of DOM access; their tests run on laz-perf's Node build and a real LidarBC chunk table.

## Updating submodule data

1. Make and validate scraper/data changes inside `vendor/bcdatamapper`.
2. Commit and push the submodule change first.
3. Update the PGMaps submodule pointer without committing duplicate generated files under `public/data`.
4. Run `npm run data:sync-from-bcdatamapper` and the relevant tests/build from PGMaps.

Do not generalize this policy to app-owned files explicitly preserved by `scripts/sync-bcdatamapper-data.mjs`, or migrate other already-tracked datasets without reviewing their ownership and deployment path.

## Map stories

- `docs/project-map-stories.md` is the contract for `story-map-v1` project packages: the scene and layer schema, every `workspace.options` field, and what each `layout` replicates.
- Read its **Changing the renderer** section before editing `src/maps/project-story/`. It lists the files a new story option has to touch together, and the renderer invariants that break silently — scene cameras are re-fitted to the map pane rather than used verbatim, chrome in the `scrolly`/`slides` layouts sits in a `pointer-events-none` overlay, and the slides pane sizes itself by rendering every slide stacked.
- Story packages live in `public/data/projects/*.json` and are listed in `index.json`; regenerate that index with `npm run projects:index` after adding or renaming one.

## Forestry tools

- `docs/forestry-tool-standard.md` lists what every `/dev/forestry` tool shares, the three tool shapes, and how a map keeps its own look through the toolkit. Read it before adding a tool or a map layer.
- Every map is the toolkit's `Map`. Give a tool its look through props (`styles`, `controls`, `MapTerrain`); do not call `map.addSource` or `map.addLayer` in a page. The doc lists the exceptions.

- `LidarMap.tsx` passes one style object as both `styles`. A second object, or `fallbackStyles`, lets the toolkit call `setStyle` on a theme change, which wipes every LiDAR layer: nothing re-adds them. A saved map image takes the point cloud in deck's `onAfterRender` (`pointCloudFrame`), because its canvas reads back blank at any other time and nothing reports it. Hillshade uses `MapTerrain reliefOnly`: maplibre-gl-lidar owns the map's 3D terrain, and a plain `MapTerrain` clears it.

## Forestry visual quality

- `docs/forestry-visual-quality.md` is the contract for `/dev/forestry/visual-quality`: what each reported percentage means, what the sightline model does and does not include, and the run's cost limits.
- Read its **Drive the view** section before touching `src/pages/dev-forestry/DriveCamera.tsx`. The eye-level camera depends on MapLibre behaviour that fails silently — an omitted `roll` argument reaches `jumpTo` as `undefined` and leaves the transform's projection matrices null from then on.
- Do not move the 3D stand onto a deck.gl overlay. Under this camera `map.transform.elevation` is a camera-fitting residual (about −294 m at Tabor Mountain), not the ground under the map centre, and deck.gl derives its camera height from it — so its camera lands at sea level while MapLibre's is on the hillside, and nothing draws with no error reported anywhere. `treeLayer.ts` takes MapLibre's own `modelViewProjectionMatrix` for that reason.
- The preview's eye and tree bases read the fixed DEM mosaic through `renderedGroundSource` (`@pgmaps/geo-toolkit/terrain`, re-exported by `src/lib/forestry/terrain/terrain.ts`), because MapLibre's renderer registers a DEM sample at its pixel corner and `ElevationGrid` at its centre; on steep ground the half-pixel put the camera into the drawn hillside. Keep the analysis on `ElevationGrid`'s own reading, and never fix eye clearance from `queryTerrainElevation`, which follows rendered LOD.
- Anything that needs the camera's ground position during a drive must take the viewing station, not `map.getCenter()`. Pitched at the horizon from eye level, the map centre is kilometres away on the skyline.
- The drive camera keeps the canvas size and the vertical field of view in the pose it compares (`driveController.ts`). MapLibre keeps zoom and centre through a resize or a lens change (*View options → Lens*, a field photo), so an eye-level camera that is not placed again after *Fullscreen* or a pane drag stands up to 29 m behind its station and draws the stems behind it in front, with nothing reported.
- MapLibre publishes no camera position — `getFreeCameraOptions` is Mapbox-only and `transform.cameraPosition` is internal. `treeLayer.ts` takes the view direction from the projection matrix's w-row gradient instead, which cannot disagree with the matrix that drew the ground.
- The tree silhouettes in `impostor.ts` are generated, not assets. Keep it that way: it is what makes the stand redrawable for a different species mix, and it keeps third-party vegetation assets and their licences out of the repo.
- The road view draws sixteen tree drawings (`TREE_DRAWING_IDS`, `forest.ts`): nine species, each conifer's young form and the tall shrub. A new species goes on the **end** of `TREE_SPECIES_IDS`: every drawing's seed is keyed to its place there, and the first six are pinned. A stem's `form` is read off its stand (`CANOPY_CLOSES_AT_METERS`, the thicket), never drawn from the stem's own random stream, which would move every later stem's height and crown. The scene package and final stand name six species (`PACKAGE_SPECIES_IDS`, `packageSpecies`): the other renderers switch on species name and draw an unknown one as a spruce, so teach an engine a species before adding it there. A species added to the drawings also needs its snag curve named (`borrowedBy`, `stand/snagDecay.ts`).
- *Baked from 3D* (`impostorBake.ts`, doc section **Baked tree cards**), the road view's default, takes each card from its own detailed mesh, eight views round the stem, on the CPU: keep it free of DOM access, never bake on the GPU (the bytes must be the same on every machine and in the tests), and never ship a tree model or texture to bake from. A stem shows **one** baked view through a dither, never a blend of two: a blend ghosts every branch and stops a stand's cover being the mean of its views', which is what `screenCoverage.test.ts` pins. A card and its mesh must stay the same tree: the same `bakedTreeMesh(drawing, variant)`, the same `stemTurn`, the same palette (`drawingPalette`) and the same light (`CROWN_LIGHT_GLSL`). The bake's across runs to the camera's left, as the layer's card corners do; `impostorBake.test.ts` pins it. What the method takes from three.ez's octahedral impostor (MIT) is in `src/pages/dev-forestry/NOTICE-OCTAHEDRAL-IMPOSTOR.md`; keep it in step. `detailedTreeMesh`'s `'solid'` build is the scene package's and must not change for the first six species; the road view draws the `'cards'` build (`treeSprays.ts`, DOM-free).
- The far bands (`isFarBand`, `forestPatches.ts`; doc section **The far forest**) draw more than a card a stem: a canopy tile over the stem's own ground, the light of the hill it stands on, and a run of card below its foot. All display only. A tile never lies over open ground: `canopyReachAt` (`placeTrees`) samples its whole square and stops it short of a clearing, a block, water or ground the inventory calls open, and `farForest.test.ts` pins that and that laying tiles moves no stem. Never read a stem's `canopy` or `slope` from its own random stream, and keep a tile's cut-out on the stand's crown closure through the sight line's slant (Beer–Lambert), never a fixed cover. The run below the foot (`FAR_CARD_SKIRT_METERS`) is there because MapLibre draws distant ground lower than the stems are stood on; it never raises a tree's top. Do not try to raise the terrain's detail with `setSourceTileLodParams`: at eye level the map's zoom is about 19, and (4, 12) asked the elevation source for some 4,500 tiles.
- `forestPatches` (`DevForestryVisuals.tsx`) is keyed to what places a stem and nothing else. Adding a look setting to `forestConfiguration` must not regrow the stand: if a new field changes where or what a stem is, add it to that key; if it only changes how one is drawn, leave it out.
- `GroundRelief` lifts the terrain component's own hillshade above the road view's ground fills by `moveLayer`; it adds no layer, and it stands down over imagery. Its place is by mount order (after the ground fills and after the block's own fill, which is what colours cut ground), so keep it there in `VisualQualityLayers`; it stands down in the note screenshot look and under the analysis colours, where ground is painted to be read flat.
- The trees' light (`ForestOverlay`'s `sun`) and their shadows (`shadows`, `treeShadows.ts`) are props read each frame, never part of `forestConfiguration`: a new configuration regrows the whole stand. Shadows are drawn before the trees and write no depth, so they cover no part of one. A stem the viewing gap leaves undrawn lays no shadow (`refreshShadows`). Tree layers share one compiled program of each kind and one spray sheet a map (`sharedResources`, `treeLayer.ts`), so a layer sets every uniform it reads on every draw.
- `screenCoverage.test.ts` pins how much of the view each drawing's far card and detailed mesh (`detailedTreeMesh`) covers, holds the mesh within 15% of its card, and holds its baked card within 3% of its drawn card (`BOUGH_CARD_SCALE` and `SOLID_SPRAY_SIZE` in `treeGeometry.ts` are solved to that: solve them again after changing a mesh, a silhouette or a spray picture). A drawn shape is screening evidence, not styling: the trial measured shape alone moving a stand's screening by 10–12 points. Change those figures only on purpose, saying why. Tree shading (`look: 'lit'`) and the atlas mipmaps (`atlasMips.ts`, coverage-preserving) must never change which pixels a tree covers.
- *Detail when stopped* replaces the near cards with meshes of the **same** stems (positions, heights, crown widths) only while the frame's matrix is unchanged for `DETAIL_SETTLE_MS`; never let it place stems of its own or stay on while the view moves.
- A stand's species come from its whole VRI record (`SPECIES_CD_1…6`/`SPECIES_PCT_1…6`, `speciesMixFromInventory`), and non-treed VRI ground grows no regional mix (`groundCoverFromBclcs`). Slash, edge rows and road scars (`harvestedGround.ts`) are display only; keep them out of every reported figure.
- Green-up height is area-weighted over slope classes, per the 1998 procedure's Step 5 — not `vegHeightForSlope(meanSlope)`. Table 6 is a step function, so the two disagree on mixed ground. `analysis.ts` accumulates it per sample; do not recompute it from `meanSlopePercent` in a panel.
- The planimetric denominator is the landform's **treed** area, per the 1998 procedure's "total green (forested) portion". It comes from VRI rank-1's `BCLCS_LEVEL_2`, live from DataBC's WFS (`bcVegetationInventory.ts`) — not the ArcGIS service, which carries only the VRI _Dead_ layer. Dividing by the whole landform reads the figure about 27% low at Tabor Mountain, enough to cross a class.
- In `bcVegetationInventory.ts` the bounding box goes in `CQL_FILTER`, never the WFS `bbox` parameter: WFS 2.0 with `EPSG:4326` is latitude-first, CQL's `BBOX` is longitude-first, and mixing them silently returns the wrong part of BC. Keep `propertyName` narrow too — the layer has 189 attributes and GeoServer will not generalise geometry.
- Never put `glyphs: ''` in a stubbed MapLibre style. The style then never finishes loading, `isLoaded` stays false, and every effect gated on it no-ops while the tests still pass — which hid 3D terrain and the 3D stand being switched off in the whole forestry e2e suite. Assert map state (`getTerrain()`, a layer id) rather than the sidebar text describing it.
- `vqo.ts` holds two threshold scales on purpose: perspective-view ranges define the objective, planimetric ranges are the timber-supply proxy, and they are not interchangeable. Judge a number against the scale it was measured on.
- Visual sensitivity units and EVQO are read live from DataBC's WFS (`queryVisualInventory`, `visualInventoryQuery.ts`, `REC_VISUAL_LANDSCAPE_INVENTORY`) everywhere on the page, *Find a landform* included, with no stored copy and no fallback: a failed read is an error with a retry, never an empty inventory. Never read the ArcGIS `MapServer/6` layer (it stops at 10,000 of the 60,499 polygons) or reintroduce a snapshot built from it; a complete full-resolution copy is 200–270 MB gzipped and simplification distorts small units (13% area change at 1 m). Keep source coordinates intact. A nearest sensitivity unit is a review candidate, never an automatically verified visual landform.
- Tree placement tests every candidate stem against the clearings, and basemap water arrives as tile-sized multipolygons: test many points through `preparePolygons` (`visibility.ts`: parts with their own boxes, rings banded by latitude, exact `pointInPolygon` answers), never `pointInPolygon` in a loop. Before it, one patch took about 870 ms and the road view drew 1 frame a second (`preparedPolygons.test.ts` pins the equivalence).
- The page is a shared `TiledWorkspace` (`visualsWorkspace.ts`) with **two maps**: the plan map and the road view's own eye-level map, mounted only while the road view is open and on screen. The scene's layers are `VisualQualityLayers` with `mode="plan" | "eye"`; add a layer there once, choosing its map, never a `drive.active` switch in one shared map. `DriveCamera`, terrain, the tree stand, haze, the photo overlay and *Save viewpoint* / *Image* capture use the road view's map (`eyeMapRef`); the table bridge, legend and anything read from the basemap use the plan (`mapRef`). The plan's viewer marker is `MapViewerCone` fed by the pose's ground position, rounded so it is one `setData` a few times a second. The Viewpoint summary (`viewpointSummaryRows.ts`, DOM-free) reads the run and names every percentage's scale; never recompute a figure there. The e2e spec's `readMapState` reads a map by its pane (`visuals-road-view`, `visuals-plan-map`).
- `MapSectionLayout` gives the page one fixed-height sidebar slot and that slot does not scroll, so everything the sidebar renders — `AssessmentPanel` included — belongs inside `MapSidebarShell`'s scroll container, which is what the step slot props on `Sidebar.tsx` (`setup`, `visit`, `landformScope`, `designReview`, `report`, …) are for. Stacked beside the shell instead, a panel pushes the shell's lower half and the bottom of its scroll port off the screen, where scrolling never reaches them; nothing overflows visibly to give it away.
- The sidebar follows the VIA handbook's five steps; the rating rules live in `via.ts` (see the doc's **The sidebar follows the VIA handbook's five steps**). The ocular class is always a reviewer input, Table 2 is read as printed rather than from the editable planning thresholds, and `viaReview` stays out of `sceneFingerprint` so editing a judgement never stales the run. The steps are tabs with every panel mounted but `hidden` when not selected, so an e2e test must bring a step forward (`showStep` in `forestry-visual-quality.spec.ts`) before touching its controls. Give each job one place in the sidebar — don't re-add a second draw/import/play control for something another section or the road-view panel already does.
- Step 2's field photo (`mapillary.ts`, `photoPose.ts`, `useFieldPhoto.ts`) needs only a Mapillary **client token**, `VITE_MAPILLARY_TOKEN` in the git-ignored `.env.local`; never add a client secret or commit a token. Mapillary poses follow OpenSfM (camera x right, y down, z forward; focal as a fraction of the longer side), and `orientationFromRotation` must keep reproducing the image's own `computed_compass_angle` — the unit test pins it to a real image. The Playwright web server sets a dummy token and the tests stub the Graph API.
- Any pitch the drive camera is handed goes through `horizonSafePitch` (`driveMath.ts`). A map pitch of exactly 90° — a lined-up photo looking level — crashes MapLibre's GPU process with 3D terrain on, and the page only shows "target crashed".
- A partial-cut block is not cleared ground: `analysis.ts` keeps it out of the proposal ledger and the screening canopy clearing, and `via.ts` adds its Table 6 equivalent to X only when the run sees it. Do not feed existing openings' `PERCENT_CLEARCUT` through Table 6 — it is not volume removed. The block's retention and partial-cut numbers stay out of `AnalysisInput`; only `harvestSystem` changes the run. The class pass paints a partial cut in its own class (`partialIn`/`partialOut`), outlined as a block but never counted as Proposed, and the sheet states its Table 6 figure beside the pixel figure.
- The drawn stand's density is calibrated, not styled: each crown's width comes from `crownWidthForClosure` so every distance band shows the stand's VRI crown closure (or `REGIONAL_STAND`). Do not reintroduce per-band width multipliers or species-constant crown widths — they closed the near stand to ~80% and left far hills at ~10% against a real 45–50%.
- `landformFromTerrain.ts` returns a **candidate**; never adopt it into a scene without the reviewer's click, and keep `blockOnly` honest — a block on a valley floor has no landform to take a share of.
- The Visuals paragraph (`visualsNarrative.ts`) is a draft the reviewer signs: keep `viaReview.visualsNote` the reviewer's, never overwrite it from the run, and change `visualsNarrative.test.ts`'s reference paragraphs only with the planner's wording. Inventory viewpoints come from the WFS (`viewpointInventory.ts`): MapServer layer 5 returns no rows, every row's expiry is past, and arrow `COMPASS_BEARING` is always 0, so a bearing is read from the joined viewpoint to the arrow's farthest vertex.
- Road-view haze is `hazeRings` (`driveMath.ts`), draped rings faded by Koschmieder's law, not MapLibre's sky fog: at eye level its fog depth starts at a near plane about 11.5 × the camera's elevation above sea level (about 8 km at 700 m) and moves with the elevation residual. Haze and the landform drape are display only and off by default. `docs/forestry-visual-quality-planner-review-2026-11-10.md` tracks what the planner asked for and what is left.
- The visual measures (`visualMeasures.ts`) are a draft the reviewer signs, like the Visuals paragraph: keep `viaReview.visualMeasures` the reviewer's and never overwrite it from the draft. In the block note they sit on their own "Visual measures" sheet so *Other Considerations* keeps B2, C2 and its screenshots where they are. The `retained` mask kind is shown as *Wildlife tree patch / retention*; never rename the stored value, which saved scenes carry.
- The block note (`blockNote.ts`) writes Excel in the planner's layout ("Visuals" in B2, the paragraph in C2, screenshots below) and a Canfor-style PDF; keep it free of DOM, with exceljs and jsPDF passed in. Screenshots are taken at *Save viewpoint*, not re-rendered at export.
- Satellite imagery is a layer under the basemap's first label layer (`SatelliteImagery`, `src/components/ui/map-satellite-imagery.tsx`, shared with the road-design plan), capped at z18; a `styles` swap would `setStyle` the 3D timber away, and Esri's z19 in rural BC is a grey placeholder tile.
- The road view's map is mounted while `drive.active || roadViewHeld`, not `drive.active` alone: standing at a viewpoint or going back to the road re-runs the analysis, and unmounting the map for that round trip rebuilt its WebGL context, style, tiles, terrain and shaders (measured about 1.4 s and a visible reload). Set `roadViewHeld` when a swap starts with the road view open; it clears when the road view opens again, on error, on cancel and on leaving.
- While the road view is open a plain click on the plan moves it (`PlanClickToMove`, snapped to the road), so plan-mode layers that act on click (inspecting a sample, adopting a sensitivity unit) stand aside while `drive.active`; an inventory viewpoint click still stands there. A new plan layer that takes clicks must choose too. Every plan layer needs a `PlanLegendKey` and a legend row (`planLayers.ts`); the basemap and reference overlays go in the map's `MapLayersControl`, not the legend.
- The road view's frame loops sleep when nothing moves (`DriveCamera.tsx`'s `DRIVE_AWAKE_MS`, `ForestOverlay.tsx`'s `FOREST_IDLE_POLL_MS`): anything new that moves the drive camera must wake it (`wakeRef`, a key, map `data` or `resize`), or the camera stays where it was.
- What the road view draws only to guide the reviewer (the inventory arrows of the viewpoint stood at) goes on the `ROAD_VIEW_GUIDE_SOURCE` source (`mapCapture.ts`): `captureMapImage`, `captureFramed` and `captureAtCamera` hide every layer on it for the picture and put it back, so a guide never prints in a saved view, a before render or a report figure. Add a new guide to that source, never as a layer a capture would have to know by id.
- Fills drawn only for show on the eye-level map pass `interactive={false}`: with 3D terrain on, each hover query is a synchronous GPU readback (1.6 s of `readPixels` in a 49 s trace). Pose reports reach page state rounded (the eye to about 10 m); never put a raw per-frame pose in React state.
- Which edits stale the run: review records (`viaReview`: stage, crew checklist, visual measures, the Visuals paragraph) never do; a complete field-confirmed green-up check and a wildlife tree patch (`retained` mask) do, because they change the figures; tree-free areas, views of interest, basemap and legend switches never do (`treeFreeAreas` and `viewsOfInterest` are deleted in `sceneFingerprint` and absent from `AnalysisInput`; adopting a view's landform does stale it, because it adds a landform target). The modelled green-up share is always kept beside a field override, and every printed figure names which one it used. The rationale for the field workflow is the doc's **Why the field workflow is shaped this way**; the traces behind the performance rules are **Road view performance**.
- Step 3's recovery timeline, green-up age sensitivity and drought panel, and Save & export's *Castor constraint* (doc section **Assessment workspace tools**, **Save & export**): a loaded Castor curve keeps its heights as given (`castorCurves.ts`), and the library and block assignments live in the workspace, never the scene. A partial cut harvested in an earlier year keeps its Table 6 figure until its gaps reach green-up height; never grow its residual trees, because Table 6 rises with residual height. The green-up sensitivity changes only `settings.greenUpAgeYears` on copies and never the scene's default. forDRAT ratings are context only, never a run input or a green-up change; the soil moisture regime is always the reviewer's, and only unambiguous VRI codes are rated (`FORDRAT_SPECIES_FOR_VRI`). The constraint's height and percentage are the run's and `resolveThreshold`'s, never re-derived, and its denominator difference stays stated, not converted. Keep `castorCurves.ts`, `recoverySummary.ts`, `castorConstraint.ts` and `droughtRisk.ts` (`fetch` passed in) free of DOM and network access.
- Keep `impostorBake.ts` and `treeSprays.ts` free of DOM and network access.
- Keep `planLayers.ts`, `treeFreeAreas.ts`, `viewpointStand.ts`, `sceneCover.ts`, `scenePosting.ts`, `skylineReach.ts`, `engineCapture.ts`, `finalStand.ts`, `exifPose.ts`, `matchedCamera.ts`, `fieldChecklist.ts`, `fieldBrief.ts`, `visualMeasures.ts`, `greenUp.ts` and `runRevision.ts` free of DOM and network access (jsPDF passed in for the brief, as for the block note).
- View options → *Renderer* (`externalRenderers.ts`, `ExternalRoadRenderer.tsx`; doc section **Choosing the renderer**) lets another engine (threejs-worldgen, Nanite Forest) draw the road view over PGMaps' map, fed the scene package, the drive camera and the light and weather (`pgmaps-environment`) by `postMessage`. The environment's date and time are the site's clock (`siteTimeZone`, sent with the UTC instant), never the computer's, and an engine reports the sun its light came from beside the one asked for. Both engines run as workers PGMaps starts, drawing into an OffscreenCanvas (`engineChannel.ts`, `EngineSurface.tsx`): each is built from its submodule (`vendor/threejs-nanites`, `vendor/threejs-worldgen`) into the git-ignored `public/engines/<id>/` by `npm run engines:build` (`scripts/build-engines.mjs`, also run by `predev` and `prebuild`; each engine's own `build:pgmaps-worker`). Never import an engine into `src/` or bundle it with the app; change it in its own repository, then move the submodule pointer. Keep the engines' folders out of Vite's dependency scan (`optimizeDeps.entries` in `vite.config.ts`): their demo pages import their own packages, and scanned from here they stop pre-bundling for the whole app. An engine runs as its own page in a `pointer-events-none` frame only when its `VITE_FORESTRY_*_URL` names one (a release, or its dev server, to compare against); `engineKindOf` tells the two apart by the address. The bridges post and listen only through an `EngineChannel`, never a frame's window or a worker directly. - Sheet maps are north-up Web Mercator with the scale stated at the frame's centre latitude. Gross area is planar BC Albers, and a slope on a class break belongs to the class below it. Sheets carry no third-party logo or company name: the logo slot is the user's own.
- A map symbol is defined once, in `src/lib/forestry/blockSheet/symbolCatalogue.ts` or `styles.ts`, and drawn only through `src/lib/mapSheet/symbols.ts` (sheet, legend swatches, gallery) and `mapSymbols.ts` (MapLibre). Where a reference legend disagrees with its map, use the map value and add the case to `symbolMismatches.ts`.
- Point icons in `src/lib/mapSheet/icons.ts` are PGMaps' own drawings. Never extract, trace or embed symbol-font glyphs, and never commit the reference PDFs, their renders, block names, coordinates or branding; credit the specs generically ("ArcGIS Pro block-map sheets supplied by a BC licensee, November 2026").
- Map patterns and icons go through `keepSymbolImages`, which also answers `styleimagemissing`; a plain `map.addImage` disappears on the next `setStyle`. Image ids hash the drawing, so a changed colour gets a new image.
- The road plan, its legend and the block sheet all classify context through `contextSheetKey` (`planSheetSymbols.ts`). With sheet symbols on, keep `road-context-fill` at opacity 0 rather than hidden, because clicks on harvest areas query it.
- Keep `symbols.ts`, `icons.ts`, `symbolRaster.ts`, `mapSymbols.ts`, `symbolSvg.ts`, `symbolCatalogue.ts`, `symbolMismatches.ts` and `gallerySheets.ts` free of DOM and network access; `sheetPng.ts` is browser-only. ## LiDAR snapshots

- `src/pages/dev-lidar/*.generated.json` pin the exact bytes of the analysis products CI builds and deploys. Regenerate them from CI's products, never from a local build: the same code on macOS differs in nearly every product's bytes. When a snapshot check fails, the deploy job regenerates them from its own products and uploads `lidar-snapshots-regenerated`; commit that artifact.
- `scripts/lidar/regenerate_snapshots.py` runs every product-based generator in dependency order. The tree benchmark (R/lidR/PointTree) and building models (Roofer) are not rerun in CI; re-pin them only after checking their plots or footprints are unaffected.
- `process.py` jitters the ground TIN's block centroids by a hashed ±1e-4 cell and rounds interpolated terrain to the millimetre. Without that, cocircular centroids triangulate differently per machine and moved terrain by up to 0.6 m between builds. Keep workflows on `ubuntu-24.04` rather than `ubuntu-latest`.

## AVAST volume

- `docs/forestry-avast-volume.md` is the contract for `/dev/forestry/avast-volume`, which runs the AVAST Volume Calculation procedure (Parts 1–3) and exports the planning workbook and a File Geodatabase.
- Volume is Σ(piece area × piece density) in BC Albers hectares — never a sum or mean of `CMM_m3ha`, never gross area × one density. The LiDAR factor scales AVAST volume only: never area, never a direct-LiDAR block, and a derived factor is total LiDAR ÷ total AVAST over the common footprint.
- The first three workbook sheets mirror `Dunkley_Volume_Summary_All_Blocks.xlsx` (sheet order, row 5 headers, `G`/`K` formulas, Management Summary `SUMIFS` on `K = "OK"`) so rows paste between them; change `workbookRows.ts` and `excel.ts` together.
- Every gdal3.js call goes through `gdal.ts` (`exclusive` queue, one WORKERFS mount for all inputs). Type geodatabase columns through `layerGeoJson`, not SQLite-dialect CASTs, which type computed columns from the first row.
- Keep `geometry.ts`, `slope.ts`, `overlay.ts`, `report.ts`, `run.ts`, `inputs.ts`, `workbookRows.ts`, `outputs.ts` and `projection.ts` free of DOM and network access.

## Shared UI

- `docs/shared-ui.md` lists the shared sidebar, list, dialog, legend and formatting building blocks. Use them before hand-rolling markup; when a page needs something they cannot express, add an opt-in prop to the shared piece instead of copying it.
- Design tokens (corner radius, status colours, type sizes, control heights) follow `docs/shared-ui.md`, **Design tokens**: names in the toolkit's `tailwind-theme.mjs`, values only in `src/index.css`, whose rules also target `.geo-toolkit` so they reach inside workspaces. Never write a pixel radius, a `dark:` partner for a status colour, or an `h-*` override on a `Button`; the forestry tools' lint rule rejects the class forms.
- A colour a person picks is `ColorField`; an area pattern, a line style or a layer's whole look is `PatternField`, `LineDashField`, `SymbolStyleEditor` or `SymbolField` (`docs/shared-ui.md`, **Colours, patterns and line styles**). Never an `<input type="color">` or a page's own picker. `ColorField`'s `onChange` fires once, when a drag ends: write the project there, and use `onPreview` only where following the drag is cheap. A stored look is a `SymbolStyle` holding only what the person set, drawn as a `SheetSymbol`; its pattern and line-style ids are saved in project files, so rename a label, never an id. A colour ramp is `RampField` over the toolkit's `COLOR_RAMPS`. A width in metres on the ground is divided by cos(latitude) before it reaches `referenceLineWidth`, or Mercator draws it 1.7× thin here. `qmlStyle.ts` reads a QGIS style file from the format alone and returns a note for everything it leaves out. Keep `symbolStyle.ts`, `qmlStyle.ts` and `referenceStyles.ts` free of DOM and network access. Only the person's own content is pickable: catalogue symbols, figure presets, status colours and legend ramps stay fixed. E2E specs pick a colour with `tests/e2e/color-field.ts`.
- The application has one scrollbar (`src/lib/overlayScrollbars/install.ts`, installed in `main.tsx`; `docs/shared-ui.md`, **Scrollbars**): every native scrollbar is hidden and a thumb is drawn over the scroller in use, for every scroller in the app and the toolkit, both axes. Never add `scrollbar-gutter`, a `::-webkit-scrollbar` or `scrollbar-width: thin` rule, or a scroll-area component: change the look once in `.overlay-scrollbar` (`src/index.css`) and the behaviour in `install.ts`. A scroller that shows no bar on purpose sets `--overlay-scrollbar: none` (or Tailwind's `[scrollbar-width:none]`); one that must keep the browser's own carries `data-native-scrollbar`. Keep `overlayScrollbars/geometry.ts` free of DOM access.
- Measure an element through `useElementSize`, fold by a size through `useSizeFold`, and give a sideways strip its arrows and wheel through `useScrollEdges` and `useHorizontalWheel` (`docs/shared-ui.md`, **Measured sizes**), never a component's own `ResizeObserver` for a size kept in state or React `onWheel` (passive: its `preventDefault` is ignored). A layout that switches at a measured size almost always changes that size: without `unfoldFrom` above `foldBelow` by more than the switch moves it, it flips every frame with nothing reported, as the road designer's charts did against the panel's grip reserve.
- Dropdowns use the shared styled select (`StyledSelect`, or `SelectField` around it; `docs/shared-ui.md`, **Dropdowns**); a native `<select>` only for multi-select. E2E specs drive them with `tests/e2e/styled-select.ts`, not `selectOption`.
- A search dialog is `SearchPalette` (`src/components/ui/search-palette.tsx`; `docs/shared-ui.md`, **Search palette**): the site search and the ribbon's Find tools are both it. Never give a search its own dialog markup or CSS, and never position the palette with a Tailwind `translate-*` class: it resets the dialog's centring and puts the box off-centre.
- Shared toolkit implementations now live in `packages/geo-toolkit`; the existing application paths are compatibility exports or PG Maps adapters. Read `docs/toolkit-extraction.md` before changing package boundaries. Keep the package free of imports back into PG Maps, application aliases, data preparation and domain defaults.

- The package's own checks (boundaries, lint, format, tests, watch, independent consumer, packed artifact, MapLibre 6) run in the `ahzs645/geo-toolkit` repository's CI; PG Maps no longer keeps copies of them. Change the package there first and confirm its CI passes before moving the submodule pointer. PG Maps' `checks.yml` then verifies the pinned commit against the application: `tsc -b`, lint and the full unit suite, including the package's tests against PG Maps' dependency versions.
- Keep `npm run toolkit:watch` running alongside Vite for live package edits; a failed build retains the last valid exports until the source is corrected.
- Every map gets the right-click menu, status bar, camera keys (N, U, R, ?) and colour-vision preview through the application's `Map`/`SharedMap` (`map-essentials.tsx`; `docs/shared-ui.md`, **Map essentials**).
