# PGMaps Agent Instructions

## CI workflows

- Only `checks.yml` (typecheck, lint, format, unit tests) and `deploy.yml` (Pages build; deploys on `main`) run automatically.
- Feature-specific browser or reference suites (forest drought, forestry roads, roads vs native R, MMGIS, Nechako, viewshed and any new one) are `workflow_dispatch` only. Do not add `pull_request` or `push` triggers to them; run them by hand (Actions → Run workflow, choosing the PR branch) when a change needs that evidence.

## Scraper-owned data

- `vendor/bcdatamapper` is the Git submodule and source of truth for scraper code, source archives, and deployable scraper snapshots.
- Treat paths copied by `scripts/sync-bcdatamapper-data.mjs` into `public/data` as generated build output. Do not force-add ignored copies of those files to the PGMaps repository.
- In particular, WARS artifacts belong only in `vendor/bcdatamapper/datascrapers/bc/wars/output`. Keep the manifest and deterministic compressed `*.gz` snapshots there; generate `public/data/wars` with `npm run data:sync-from-bcdatamapper`.
- Keep deployment checkout configured with recursive submodules. A build that does not initialize `vendor/bcdatamapper` cannot assemble scraper-owned data.
- `vendor/canadadatamapper` holds national (Canada-wide) scrapers under the same rules; `scripts/sync-bcdatamapper-data.mjs` copies its `canadaPathMappings` too, and the deploy cache key includes both submodule revisions. ISED cell sites land at `public/data/canada/cell-sites`. Build towers from ISED's `Site_Data_Extract_FX.zip`, never by scraping ertyu.org, whose `robots.txt` disallows automated clients.

## Data hosts

- `docs/data-hosts.md` is the contract for `src/config/data-hosts.json`, which lists the `public/data` folders served from another host. Moving a folder off Pages is one entry there; the sync script, deploy cache key and service worker follow it.
- `cciss`, `census`, `citypg`, `drought`, `forest` and `network-availability` are served by bcdatamapper's own Pages site, not this build. Their layout lives in `vendor/bcdatamapper/pages/site.json`; do not re-add their mappings to `scripts/sync-bcdatamapper-data.mjs`. A bcdatamapper data push reaches the live app without a deploy, and `scripts/check-data-hosts.mjs` warns in the deploy when the live folders differ from the pinned submodule.
- Those folders are not in `public/data` during a build or a unit run. A build script that needs one reads it through `createDataSourceResolver` (`scripts/lib/data-source-path.mjs`), and a test reads the submodule's copy. The deploy only copies what bcdatamapper commits, already built: do not add a step that builds scraper output into `public/data`.
- bcdatamapper's Pages site is 617 MB of its 1 GB limit. Publish only what the app loads: `canada-admin` (202 MB) sat there unread until it was removed, because the story reads PMTiles on R2. Check for a reference in `src` before adding a folder, and leave full-detail sources (the `BCMoH` originals, province-wide `BCFWA` files) out.
- Resolve every data URL with `withBase` (`src/lib/dataUrl.ts`), directly or through `fetchJson`/`fetchBytes`. A bare `'/data/...'` handed to MapLibre, deck.gl, a worker or a link, or a URL built from `import.meta.env.BASE_URL`, always loads from this site and breaks once its folder moves.

## LiDAR point cloud tiles

- `vendor/pgmaps-lidar-data` builds and publishes the EPT tiles. Its Release stores them and its own Pages site serves them to the browser; PGMaps loads them at runtime and does not deploy them. Do not bring them back into `dist`: at 495 MB they put this site over GitHub's 1 GB Pages limit, which `deploy.yml` now warns about at 900 MB compressed.
- Browsers cannot read a GitHub Release asset, because GitHub sends no CORS headers on those downloads. A Release can store data but cannot serve it to the app.
- Pages keys a deployment by commit, and a cancelled commit cannot deploy again. Retry a timed-out deploy with a new commit, not a rerun.
- Import & data reads a LAS/LAZ too large to load whole one chunk at a time (`largeLaz*.ts`): `src/lib/lidar/lazChunkTable.ts` decodes LAZ's chunk table, a port of LASzip (Apache-2.0, `NOTICE-LASZIP.md`), and laz-perf's `ChunkDecoder` decodes each chunk in a worker. Never read such a file with `arrayBuffer()` or laz-perf's whole-file `LASZip`: a LidarBC tile is up to 2.8 GB and 3–5 GB unpacked, past WebAssembly's 4 GB. Keep `lazChunkTable.ts`, `largeLaz.ts` and `largeLazDecode.ts` free of DOM access; their tests run on laz-perf's Node build and a real LidarBC chunk table.

## Updating submodule data

1. Make and validate scraper/data changes inside `vendor/bcdatamapper`.
2. Commit and push the submodule change first.
3. Update the PGMaps submodule pointer without committing duplicate generated files under `public/data`.
4. Run `npm run data:sync-from-bcdatamapper` and the relevant tests/build from PGMaps.

Do not generalize this policy to app-owned files explicitly preserved by `scripts/sync-bcdatamapper-data.mjs`, or migrate other already-tracked datasets without reviewing their ownership and deployment path.

## Map stories

- `docs/project-map-stories.md` is the contract for `story-map-v1` project packages: the scene and layer schema, every `workspace.options` field, and what each `layout` replicates.
- Read its **Changing the renderer** section before editing `src/maps/project-story/`. It lists the files a new story option has to touch together, and the renderer invariants that break silently — scene cameras are re-fitted to the map pane rather than used verbatim, chrome in the `scrolly`/`slides` layouts sits in a `pointer-events-none` overlay, and the slides pane sizes itself by rendering every slide stacked.
- Story packages live in `public/data/projects/*.json` and are listed in `index.json`; regenerate that index with `npm run projects:index` after adding or renaming one.

## Forestry tools

- `docs/forestry-tool-standard.md` lists what every `/dev/forestry` tool shares, the three tool shapes, and how a map keeps its own look through the toolkit. Read it before adding a tool or a map layer.
- Every map is the toolkit's `Map`. Give a tool its look through props (`styles`, `controls`, `MapTerrain`); do not call `map.addSource` or `map.addLayer` in a page. The doc lists the exceptions.

- `LidarMap.tsx` passes one style object as both `styles`. A second object, or `fallbackStyles`, lets the toolkit call `setStyle` on a theme change, which wipes every LiDAR layer: nothing re-adds them. A saved map image takes the point cloud in deck's `onAfterRender` (`pointCloudFrame`), because its canvas reads back blank at any other time and nothing reports it. Hillshade uses `MapTerrain reliefOnly`: maplibre-gl-lidar owns the map's 3D terrain, and a plain `MapTerrain` clears it.

## Forestry visual quality

- `docs/forestry-visual-quality.md` is the contract for `/dev/forestry/visual-quality`: what each reported percentage means, what the sightline model does and does not include, and the run's cost limits.
- Read its **Drive the view** section before touching `src/pages/dev-forestry/DriveCamera.tsx`. The eye-level camera depends on MapLibre behaviour that fails silently — an omitted `roll` argument reaches `jumpTo` as `undefined` and leaves the transform's projection matrices null from then on.
- Do not move the 3D stand onto a deck.gl overlay. Under this camera `map.transform.elevation` is a camera-fitting residual (about −294 m at Tabor Mountain), not the ground under the map centre, and deck.gl derives its camera height from it — so its camera lands at sea level while MapLibre's is on the hillside, and nothing draws with no error reported anywhere. `treeLayer.ts` takes MapLibre's own `modelViewProjectionMatrix` for that reason.
- The preview's eye and tree bases read the fixed DEM mosaic through `renderedGroundSource` (`terrain.ts`), because MapLibre's renderer registers a DEM sample at its pixel corner and `ElevationGrid` at its centre; on steep ground the half-pixel put the camera into the drawn hillside. Keep the analysis on `ElevationGrid`'s own reading, and never fix eye clearance from `queryTerrainElevation`, which follows rendered LOD.
- Anything that needs the camera's ground position during a drive must take the viewing station, not `map.getCenter()`. Pitched at the horizon from eye level, the map centre is kilometres away on the skyline.
- MapLibre publishes no camera position — `getFreeCameraOptions` is Mapbox-only and `transform.cameraPosition` is internal. `treeLayer.ts` takes the view direction from the projection matrix's w-row gradient instead, which cannot disagree with the matrix that drew the ground.
- The tree silhouettes in `impostor.ts` are generated, not assets. Keep it that way: it is what makes the stand redrawable for a different species mix, and it keeps third-party vegetation assets and their licences out of the repo.
- Green-up height is area-weighted over slope classes, per the 1998 procedure's Step 5 — not `vegHeightForSlope(meanSlope)`. Table 6 is a step function, so the two disagree on mixed ground. `analysis.ts` accumulates it per sample; do not recompute it from `meanSlopePercent` in a panel.
- The planimetric denominator is the landform's **treed** area, per the 1998 procedure's "total green (forested) portion". It comes from VRI rank-1's `BCLCS_LEVEL_2`, live from DataBC's WFS (`bcVegetationInventory.ts`) — not the ArcGIS service, which carries only the VRI _Dead_ layer. Dividing by the whole landform reads the figure about 27% low at Tabor Mountain, enough to cross a class.
- In `bcVegetationInventory.ts` the bounding box goes in `CQL_FILTER`, never the WFS `bbox` parameter: WFS 2.0 with `EPSG:4326` is latitude-first, CQL's `BBOX` is longitude-first, and mixing them silently returns the wrong part of BC. Keep `propertyName` narrow too — the layer has 189 attributes and GeoServer will not generalise geometry.
- Never put `glyphs: ''` in a stubbed MapLibre style. The style then never finishes loading, `isLoaded` stays false, and every effect gated on it no-ops while the tests still pass — which hid 3D terrain and the 3D stand being switched off in the whole forestry e2e suite. Assert map state (`getTerrain()`, a layer id) rather than the sidebar text describing it.
- `vqo.ts` holds two threshold scales on purpose: perspective-view ranges define the objective, planimetric ranges are the timber-supply proxy, and they are not interchangeable. Judge a number against the scale it was measured on.
- Visual sensitivity units and EVQO are read live from DataBC's WFS (`queryVisualInventory`, `REC_VISUAL_LANDSCAPE_INVENTORY`), never the ArcGIS `MapServer/6` layer: that layer stops at 10,000 of the 60,499 polygons, and the `bcdatamapper` snapshot built from it (`visualInventorySnapshot.ts`) misses most of BC, Purden Lake included. The snapshot is only the WFS fallback and *Find a landform*'s source until it is rebuilt from the WFS. Keep source coordinates intact: a 30 m simplification distorted small units. A nearest sensitivity unit is a review candidate, never an automatically verified visual landform.
- `MapSectionLayout` gives the page one fixed-height sidebar slot and that slot does not scroll, so everything the sidebar renders — `AssessmentPanel` included — belongs inside `MapSidebarShell`'s scroll container, which is what the step slot props on `Sidebar.tsx` (`setup`, `visit`, `landformScope`, `designReview`, `report`, …) are for. Stacked beside the shell instead, a panel pushes the shell's lower half and the bottom of its scroll port off the screen, where scrolling never reaches them; nothing overflows visibly to give it away.
- The sidebar follows the VIA handbook's five steps; the rating rules live in `via.ts` (see the doc's **The sidebar follows the VIA handbook's five steps**). The ocular class is always a reviewer input, Table 2 is read as printed rather than from the editable planning thresholds, and `viaReview` stays out of `sceneFingerprint` so editing a judgement never stales the run. The steps are tabs with every panel mounted but `hidden` when not selected, so an e2e test must bring a step forward (`showStep` in `forestry-visual-quality.spec.ts`) before touching its controls. Give each job one place in the sidebar — don't re-add a second draw/import/play control for something another section or the road-view panel already does.
- Step 2's field photo (`mapillary.ts`, `photoPose.ts`, `useFieldPhoto.ts`) needs only a Mapillary **client token**, `VITE_MAPILLARY_TOKEN` in the git-ignored `.env.local`; never add a client secret or commit a token. Mapillary poses follow OpenSfM (camera x right, y down, z forward; focal as a fraction of the longer side), and `orientationFromRotation` must keep reproducing the image's own `computed_compass_angle` — the unit test pins it to a real image. The Playwright web server sets a dummy token and the tests stub the Graph API.
- Any pitch the drive camera is handed goes through `horizonSafePitch` (`driveMath.ts`). A map pitch of exactly 90° — a lined-up photo looking level — crashes MapLibre's GPU process with 3D terrain on, and the page only shows "target crashed".
- A partial-cut block is not cleared ground: `analysis.ts` keeps it out of the proposal ledger and the screening canopy clearing, and `via.ts` adds its Table 6 equivalent to X only when the run sees it. Do not feed existing openings' `PERCENT_CLEARCUT` through Table 6 — it is not volume removed. The block's retention and partial-cut numbers stay out of `AnalysisInput`; only `harvestSystem` changes the run.
- The drawn stand's density is calibrated, not styled: each crown's width comes from `crownWidthForClosure` so every distance band shows the stand's VRI crown closure (or `REGIONAL_STAND`). Do not reintroduce per-band width multipliers or species-constant crown widths — they closed the near stand to ~80% and left far hills at ~10% against a real 45–50%.
- `landformFromTerrain.ts` returns a **candidate**; never adopt it into a scene without the reviewer's click, and keep `blockOnly` honest — a block on a valley floor has no landform to take a share of.
- The Visuals paragraph (`visualsNarrative.ts`) is a draft the reviewer signs: keep `viaReview.visualsNote` the reviewer's, never overwrite it from the run, and change `visualsNarrative.test.ts`'s reference paragraphs only with the planner's wording. Inventory viewpoints come from the WFS (`viewpointInventory.ts`): MapServer layer 5 returns no rows, every row's expiry is past, and arrow `COMPASS_BEARING` is always 0, so a bearing is read from the joined viewpoint to the arrow's farthest vertex.
- Road-view haze is `hazeRings` (`driveMath.ts`), draped rings faded by Koschmieder's law, not MapLibre's sky fog: at eye level its fog depth starts at a near plane about 11.5 × the camera's elevation above sea level (about 8 km at 700 m) and moves with the elevation residual. Haze and the landform drape are display only and off by default. `docs/forestry-visual-quality-planner-review-2026-11-10.md` tracks what the planner asked for and what is left.
- The block note (`blockNote.ts`) writes Excel in the planner's layout ("Visuals" in B2, the paragraph in C2, screenshots below) and a Canfor-style PDF; keep it free of DOM, with exceljs and jsPDF passed in. Screenshots are taken at *Save viewpoint*, not re-rendered at export.
- Satellite imagery is a layer under the basemap's first label layer (`SatelliteImagery.tsx`), capped at z18; a `styles` swap would `setStyle` the 3D timber away, and Esri's z19 in rural BC is a grey placeholder tile.
- Keep `terrain.ts`, `visibility.ts`, `vqo.ts`, `via.ts`, `photoPose.ts`, `landformFromTerrain.ts`, `ridgeLayers.ts`, `visualsNarrative.ts`, `basemapContext.ts`, `shapeImport.ts`, `reverseViewshed.ts`, `roadSnap.ts`, and `forest.ts` free of DOM and network access. They carry the unit tests, and `analysis.ts` runs against any `ElevationSource`, which is what lets a run be checked outside a browser. `roadSnap.ts` takes a structural `RoadQueryMap` rather than a MapLibre map for the same reason.

## Forestry road design

- `docs/forestry-road-design.md` is the contract for `/dev/forestry/road-design`.
- The designer's interfaces (Ribbon, Guided map, Workbench, Dashboard) are arrangements of one command registry, `src/components/interfaces/workspaceCommands.ts`, laid out by `public/workspace-layouts.json` (guide `docs/forestry-road-design/workspace-layouts.md`). Never hand-build a button for a registry command in a view: render it through `CommandButton` and give it a `presentation`. A new interface is a layout entry; a new command is one registry entry plus one handler and one state in the page. Investigation availability is the registry's `investigation` flag, and editor commands are derived from `editor`. The designer opens straight into the last-used interface or `?interface=`; never gate it on the chooser again. Parse configuration by hand (`src/lib/jsonGuards.ts`): no schema library ships to the browser. The guides in `docs/forestry-road-design/` list each area's limits, assumptions and failure modes. Their "Limits and budgets" tables cite the enforcing constant, so change the guide in the same commit as the constant.
- Section offsets are negative to the left looking up-station, everywhere: engine, charts, exports and the design surface. `sectionGeometry.test.ts` and `designSurface.test.ts` pin it.
- Route searches read grades from `groundTrend.ts`, a 12 m moving mean on terrain of 3 m cells or finer, never from raw 1 m samples: micro-relief read as 30 %+ grades and left the searches finding nothing on the published LiDAR, even at 15–20 % limits. Pass `resolvedGroundWindow` to any new search. Profiles, sections and quantities keep the source terrain.
- `routeComparison.ts` must measure the cheapest road, not assume it from a preference: Shortest beat Balanced by 15 % on the LiDAR road. `assignGoals` names each row by what it measured, so never label a row from the search that made it: a Lowest cost row once cost $10,000 more than the road tagged Cheapest, because refinement prices only the build. A row with a blocker never leads, because a ground-following road looks cheap while breaking the grade limit. The drainage goal charges a flow raster rather than stream lines, which exhausted the corridor's budgets.
- `roadFromRoute` (`routeFit.ts`) turns every found route into a road (Find the best route, route alternatives, adopted skid spurs) and never keeps a fit that reads steeper than the route as found (`ROUTE_FIT_GRADE_SLACK` over `ROUTE_FIT_GRADE_WINDOW_M` chords). Without it, a spur that zig-zagged across a 15 % slope to hold 12 % was fitted straight up it within 16 m and added 30 % shorter; a route kept as found with sharp corners is the honest result.
- A plan edit must change the road. Bend handles add a point only on a drag past `MIN_BEND_DRAG_PX`, and show only on segments of `MIN_BEND_SEGMENT_PX`; a click added a point per click, and each new segment put the next handle under the cursor. Handles read `savedAlignment`, never the drag preview, because the preview changes the handle's key and remounting it mid-drag loses the drop.
- `streamClass.ts` holds the FPPR s. 47 rules, pure and versioned by `RIPARIAN_RULES`. Missing evidence must never reach S5 or S6, and a suggestion never writes `reviewedClass`. `crossingGroup` is a price label, not a riparian class; only an explicit `riparianClass` import property fills `importedClass`. See `docs/forestry-road-design/streams-and-constraints.md`.
- The road switcher lives in the header line. A row of its own takes enough height to fold the charts' legends and bands.
- The sidebar states actions and values; explanations go behind an `InfoTip`. Fold a section with `RoadSection summary`, so its row shows its live values.
- `designSurface.ts` burns ditch bottoms and uphill fill toes as continuous minimum lines after rasterizing the strips. Without that pass, a V ditch narrower than a cell aliases into a pond at every station. The regression test is the road at 17° to the grid in `hydrology.test.ts`.
- `@kninnug/constrainautor` stays pinned at an exact version. `tinSurface.ts` replaces its internal flip set for a roughly 9× speed-up on large breakline sets, so check that code before upgrading it.
- Point clouds go through `pointCloud.worker.ts`, and only the grid returns to the page. `whitebox-wasm` is imported dynamically, never from page code that loads with the route, so its 4.5 MB and 17.6 MB WASM files stay lazy.
- The selected station's dot and section line are the two features of the `road-section` source, and that source gets its own `setData` effect in `PlanView.tsx`. A scrub changes it every frame: back in the main source effect it re-sent all 15 GeoJSON sources per station and the line trailed an HTML dot by the worker's queue. The dot's HTML marker now only carries the label.
- `PlanView.tsx` passes `deferResize={false}`. The default scales the canvas during a pane drag, which leaves pixel-placed HTML markers behind until release.
- Keep `engine.ts`, `surfaceGrid.ts`, `designSurface.ts`, `hydrology.ts`, `drainageRun.ts`, `tinSurface.ts`, `lasSurface.ts`, `verticalOptimizer.ts`, `routing.ts` and `pointCloud.ts` free of DOM access. Take terrain and projections as arguments so the unit tests can run them.
- A gap in the terrain data is not a gap in the road. Quantities inside an incomplete interval stay unknown and excluded, but the mass balance carries the known earthwork across it and haul treats the road as continuous at full distance; only an entered blocked range stops material. Allocating haul run by run made a road with 4,190 m³ of usable cut against 4,151 m³ of fill borrow 1,692 m³ and waste 1,923 m³ at once, and any road pegged on the LiDAR tile hits a gap.
- Every spatial picker reads through `readSpatialImport` (`spatialImport.ts`), and nothing is classified by its geometry: a polygon is not an exclusion and a line is not a stream until the picker or the user says so. The old KML path turned an imported cutblock into an excluded constraint, which then blocked the route search to it. A point cloud with no CRS, or a terrain with no vertical datum, raises `TerrainImportQuestion`; ask, and never adopt the open terrain's datum.
- An invalid section or engineering input must not empty the road. `safeAnalyzeRoad` (`analysisResult.ts`) leaves out only the invalid field and records `calculatedInputs`; anything that prints an input beside a result reads `calculatedAlignment`, every result surface says what it leaves out, and `INVALID_INPUT_RULES` (`exportCatalog.ts`) refuses the files a contractor builds from while one stands.
- **Find the best route** ends with a road or a reason that names the limit and the place, and never says ready when nothing came back. Searches and long fits run in slices (`cooperative.ts`) so Cancel takes effect; a new long loop must yield the same way. The profile optimizer returns a profile only when the engine builds every one of its curves, and keeps control elevations unrounded: rounding the level ladder to the millimetre made the tool's own start control infeasible.
- A typed station is evaluated where it was typed (`roadStationAt`, `stationAt.ts`). Do not snap the station box to the calculated stations, and keep its text the box's own until Enter or blur: showing the resolved station after each key turned "8" into "10" and then "105".
- Keep `cooperative.ts`, `polylineFit.ts`, `routeFit.ts`, `routeAlternatives.ts`, `massHaul.ts`, `stationAt.ts`, `stationReport.ts`, `groundHorizons.ts`, `inputErrors.ts`, `analysisResult.ts`, `curveFit.ts` and `wideningEntry.ts` free of DOM access as well.
- `docs/forestry-road-design/tutorial-walkthrough-2026-11-09.md` records the acceptance run of the RoadEng tutorial through the interface, and `scripts/forestry/tutorial-kit/` builds its test files. The example alignment was picked to avoid terrain gaps, so test earthwork on a road you peg yourself. A browser-automation call that times out during a route search stops the page's script, which looks like a hung search with a dead Cancel: poll with short waits.
- The Review list is `readiness.ts`: one rule per row, three states, and a check that could not be made is `not-assessed`, never `met`. The report prints the same rows, so change a rule and `docs/forestry-road-design/review-and-standards.md` together. Keep `readiness.ts`, `crossingRegister.ts`, `designStandards.ts`, `jobStandards.ts` and `projectIssue.ts` free of DOM access. The grade limit and minimum radius stay in `project.settings`; `project.standards` only adds what those two numbers cannot say.
- `examples/forestry/access-history/reference-pairs/` is a generated reference set: 347 real blocks whose own road is named for them, their 294 setups (licence + cutting permit), Sentinel-2 first-seen dates and roads generated by the rule-based prototype. Regenerate it with the scripts in `scripts/forestry/access-research/` (README there), not by hand, and keep its README's figures in step with `docs/forestry-road-design/bc-access-research-2026-11-09.md`. Storing FTEN road section names is cleared; a production snapshot of them belongs in `vendor/bcdatamapper`. The generator is Python research code, not wired into the app: use the set as the test bench when porting rules into `routing.ts`.
- Reference projects reviewed on 10 November 2026 (`docs/forestry-road-design/field-review-and-reference-repos-2026-11-10.md`) are mostly GPL; PGMaps is MIT. Never copy, translate line by line or ship a WASM build of GPL, LGPL or unlicensed code; re-implement from the published method and cite it. `docs/forestry-road-design/reference-repo-licensing-and-conversion.md` holds the per-project routes and the open decision on shipping GPL code; change it before changing this rule. Only LANDIS-II Forest Roads (Apache-2.0) is adapted, in `skidSpurs.ts`, with `NOTICE-LANDIS.md`. Do not commit a licensee's plan blocks or roads, their map sheets, or ALSroads' sample data; env-gated tests read them from a local path.
- Skid reach (`skidReach.ts`) never counts ground as covered when it is reachable only across missing terrain: it stays unknown. The default rule is the field person's rule of thumb with "30" read as percent; change `DEFAULT_SKID_RULE` and `skid-reach-and-spurs.md` together. A spur or landing suggestion is a candidate that only **Add** makes a road, and it never relaxes a closed stream screen.
- A haul leg with no entered speed has no time, never zero; distance past the loaded roads is labelled estimated, and a haul assumed to leave by a dead end says so. Junction turns stay at or below 90° while `routing.ts` holds end headings to a fixed ±45°. The haul's loaded direction is never written into `standards.loadedDirection` without the user's click: that setting is shared by every road. Destination presets are town centres, never company mills.
- Finding a road on the terrain returns a candidate copy and never edits the record. Road-likeness alone is never proof of a road (smooth flat ground scores 1 everywhere): a found stretch or a traced segment also needs a bench in cross-section, stretches without one keep the record's line and are flagged, and below `ROAD_FIND_PARTIAL_SHARE` the record comes back unchanged. Refuse terrain coarser than `ROAD_FIND_MAX_CELL_M` (2 m), and report bench width, never drivable width.
- A steering lock is reported beside wheel fit (`lockExceeded`), never folded into `SweptManeuver.fits`. A vehicle preset is a named dimension set with a stated source; values the source does not give are marked "confirm". The road swept path keeps its follow-the-leader step because `forestry-road-switchbacks.spec.ts` pins its numbers; junction turns use the exact tractrix step.
- A D-line's `sagModel: 'mechanics'` only adds `CableAnalysis.mechanics`: never change the assumed-sag fields or the default CSV columns, and append mechanics columns after `assumptions`. The reach search never reports a reach past unknown ground (`knownFeasibleM` is a lower bound). Curvature-corrected volumes are reported only; totals, costs, mass, materials and haul use average end areas, and move together or not at all.
- Keep `skidReach.ts`, `skidSpurs.ts`, `landingSites.ts`, `haulDestination.ts`, `junctionOrientation.ts`, `haulReview.ts`, `roadGrid.ts`, `roadLikeness.ts`, `roadRelocation.ts`, `roadSlices.ts`, `roadTrace.ts`, `terrainRoadLines.ts`, `vehicleKinematics.ts`, `junctionTurn.ts`, `cableMechanics.ts`, `cableReach.ts` and `curvedVolume.ts` free of DOM and network access.

- Work brought in from the GPL reference projects follows `docs/forestry-road-design/reference-repo-licensing-and-conversion.md` (route A until the owner decides): stage-1 reviewers read the code and write functional specs; implementers work from those specs and published papers and never open the projects. Each such module carries a provenance header saying so. Do not reproduce the defects the specs list unless a test-only parity mode asks for them.
- `crates/cable-layout` (Rust, MIT) is the source of `src/pages/dev-forestry-roads/cableLayout/cable_layout.wasm`. Change the crate, run `npm run wasm:cable`, and commit the `.wasm` in the same commit; the `cable-wasm` job in `checks.yml` runs when the crate, `scripts/build-cable-wasm.mjs`, the committed `.wasm` or `checks.yml` changes (or by hand); it runs `cargo test`, rebuilds and fails on a byte mismatch, uploading `cable-layout-wasm-rebuilt` to commit.
