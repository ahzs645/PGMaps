# PGMaps Agent Instructions

## CI workflows

- Only `checks.yml` (typecheck, lint, format, unit tests) and `deploy.yml` (Pages build; deploys on `main`) run automatically.
- Feature-specific browser or reference suites (forest drought, forestry roads, roads vs native R, MMGIS, Nechako, viewshed and any new one) are `workflow_dispatch` only. Do not add `pull_request` or `push` triggers to them; run them by hand (Actions → Run workflow, choosing the PR branch) when a change needs that evidence.

## Scraper-owned data

- `vendor/bcdatamapper` is the Git submodule and source of truth for scraper code, source archives, and deployable scraper snapshots.
- Treat paths copied by `scripts/sync-bcdatamapper-data.mjs` into `public/data` as generated build output. Do not force-add ignored copies of those files to the PGMaps repository.
- In particular, WARS artifacts belong only in `vendor/bcdatamapper/datascrapers/bc/wars/output`. Keep the manifest and deterministic compressed `*.gz` snapshots there; generate `public/data/wars` with `npm run data:sync-from-bcdatamapper`.
- The walkability heatmap's factor masks are committed in bcdatamapper (`datascrapers/walkability/output/heatmap/factor_masks.json`) but built by PGMaps' `npm run walkability:build-factor-masks`, which runs the worker's own rasterization (`docs/walkability-factor-masks.md`). Never commit a copy in `public/data`, and never build them from bcdatamapper's grid builder, whose factor list is a separate copy. `walkabilityFactorMasks.test.mjs` fails when a source file they were built from changes: rebuild, commit there, then move the pointer.
- Keep deployment checkout configured with recursive submodules. A build that does not initialize `vendor/bcdatamapper` cannot assemble scraper-owned data.
- `vendor/canadadatamapper` holds national (Canada-wide) scrapers under the same rules; `scripts/sync-bcdatamapper-data.mjs` copies its `canadaPathMappings` too, and the deploy cache key includes both submodule revisions. ISED cell sites land at `public/data/canada/cell-sites`. Build towers from ISED's `Site_Data_Extract_FX.zip`, never by scraping ertyu.org, whose `robots.txt` disallows automated clients.

## Data hosts

- `docs/data-hosts.md` is the contract for `src/config/data-hosts.json`, which lists the `public/data` folders served from another host. Moving a folder off Pages is one entry there; the sync script, deploy cache key and service worker follow it.
- `cciss`, `census`, `citypg`, `drought`, `forest` and `network-availability` are served by bcdatamapper's own Pages site, not this build. Their layout lives in `vendor/bcdatamapper/pages/site.json`; do not re-add their mappings to `scripts/sync-bcdatamapper-data.mjs`. A bcdatamapper data push reaches the live app without a deploy, and `scripts/check-data-hosts.mjs` warns in the deploy when the live folders differ from the pinned submodule.
- Those folders are not in `public/data` during a build or a unit run. A build script that needs one reads it through `createDataSourceResolver` (`scripts/lib/data-source-path.mjs`), and a test reads the submodule's copy. The deploy only copies what bcdatamapper commits, already built: do not add a step that builds scraper output into `public/data`.
- bcdatamapper's Pages site is 541 MB of its 1 GB limit. Publish only what the app loads: `canada-admin` (202 MB) sat there unread until it was removed, because the story reads PMTiles on R2. Check for a reference in `src` before adding a folder, and leave full-detail sources (the `BCMoH` originals, province-wide `BCFWA` files) out.
- The Prague story (`/data/story-documents/prague`, 50 MB) is its own repository, `ahzs645/pgmaps-story-prague`, checked out as `vendor/pgmaps-story-prague` and served by its own Pages site (`docs/data-hosts.md`, **The Prague story**). Change it there, then move the pointer; never copy it back into `public/data`. A data host is named after its submodule in `vendor/`, whose `pages/site.mjs` exports `readSite` and `folderFingerprints`: `dataHosts.test.ts` and `check-data-hosts.mjs` read it by that name.
- Resolve every data URL with `withBase` (`src/lib/dataUrl.ts`), directly or through `fetchJson`/`fetchBytes`. A bare `'/data/...'` handed to MapLibre, deck.gl, a worker or a link, or a URL built from `import.meta.env.BASE_URL`, always loads from this site and breaks once its folder moves.

## Page icons

- A page's browser-tab icon is a row in `src/config/page-icons.json` (`docs/page-icons.md`), read by the shell's `usePageIcon` and by `scripts/write-spa-fallback.mjs` for each route's entry page. Never set a favicon from a page.

## Offline and caching

- `docs/app-updates-and-caching.md` is the contract for `public/sw.js`: the cache rules, the offline tools, the kept tile hosts and their limits. Change its limits tables in the same commit as the constant.
- The service worker deletes only its own cache families (`pgmaps-shell-`, `pgmaps-data-`, `pgmaps-tiles-`, `pgmaps-offline-state-`). Never go back to deleting by the bare `pgmaps-` prefix, and never name another module's cache inside one of those families: the terrain tiles (`pgmaps-terrarium-png-v1`) and the photo depth models (`pgmaps-photo-depth-v1`) were discarded on every `sw.js` change.
- Everything under `/assets/` is cache-first by folder, never by a list of extensions. Matching `.js` and `.css` alone left out MapLibre's worker (`.mjs`), so every map stayed on "Loading map data" offline with nothing reported.
- Look a stored file up with `ANY_VARIANT` (`ignoreVary`). A `crossorigin` script sends `Origin` to its own site, and a server answering `Vary: Origin` (Vite's preview) then hides every stored file from it; the unit tests cannot see this, only `tests/e2e/offline-tools.spec.ts` can.
- A tool works offline through a group in `offlinePrecache` (`vite.config.ts`) and one `useOfflineTool` call in its page (`src/lib/offline/offlineTools.ts`). The file lists are generated from the bundle (`scripts/offline-precache-plugin.ts`, `src/lib/offline/precacheManifest.ts`); never write a built file's name by hand, and keep `precacheManifest.ts` free of DOM, network and bundler types.
- The build fails when the shell passes `SHELL_BUDGET`. Fix the import that moved a library into the shell (load it with `import()`); raise the budget only on purpose.
- Add a host to `TILE_HOSTS` only when its terms allow keeping tiles. Esri World Imagery reports `exportTilesAllowed: false` and stays out. Keep only a readable `200`; never an opaque or partial response.
- Visual quality's inventory, vegetation and viewpoint reads are live, and by default nothing is kept: offline, the page opens and a run needs a connection. *Keep inventory copies* (`src/lib/offline/inventoryCopies.ts`, rule in `keptReads.ts`, DOM-free; off by default, switched in **Offline and storage**) is the one exception: each read is kept with its date and answers only the same request when DataBC cannot be reached. Never keep a copy while it is off (turning it off deletes them all), never answer a 4xx or a cancelled read from a copy, never stamp a copy with the time it was used (`readAtOf`, `copyReadAt`), and never use one silently (`InventoryCopyNotice`). Copies stay in this browser: never in a scene, a project file or an export.
- A tool that keeps a person's work in this browser calls `keepStoragePersistent()` (`src/lib/offline/persistentStorage.ts`) from its write path. Firefox asks the person, so never call it on page load.
- `tests/e2e/offline-tools.spec.ts` needs the built site and runs only by hand (`offline-tools.yml`, `workflow_dispatch`).
- Every Cache Storage cache and IndexedDB database the app opens has an entry in `STORE_CATALOGUE` (`src/lib/storage/siteStorage.ts`), with a role: `download` (fetched or derived, clearable) or `work` (a person's own). `siteStorage.test.ts` scans the source and fails on a store that is not listed. A `download` entry inside a database that also holds work names its object stores; `clearEntry` refuses a `work` entry and a whole database, and that must stay true. Keep `siteStorage.ts` free of DOM and network access.
- **Offline and storage** (`StorageDialog`, `src/components/ui/storage-dialog.tsx`) is the one panel for what is kept: never add a second clear-cache control to a page, and never offer to delete work from it. Work is removed in the tool that made it. It is imported statically by the navbar on purpose: a lazy chunk of the shell is not in the offline shell list, so the panel would not open offline.
- Measuring never opens a database that is not listed by `indexedDB.databases()`: opening one creates it. Never write `total += await …` across parallel lanes; the cache sizes lost updates that way.
- Under storage pressure the service worker gives up only tiles and data files (`relieveStorage`). Never let it trim the shell, another module's cache or anything in IndexedDB, and never let a failed cache write fail the request it was copying (`putResponse` swallows it).

## LiDAR point cloud tiles

- `vendor/pgmaps-lidar-data` builds and publishes the EPT tiles. Its Release stores them and its own Pages site serves them to the browser; PGMaps loads them at runtime and does not deploy them. Do not bring them back into `dist`: at 495 MB they put this site over GitHub's 1 GB Pages limit, which `deploy.yml` now warns about at 900 MB compressed.
- Browsers cannot read a GitHub Release asset, because GitHub sends no CORS headers on those downloads. A Release can store data but cannot serve it to the app.
- Pages keys a deployment by commit, and a cancelled commit cannot deploy again. Retry a timed-out deploy with a new commit, not a rerun.
- Import & data, and the road designer's point-cloud import when a crop is set, read a LAS/LAZ too large to load whole one chunk at a time (`src/lib/lidar/largeLaz*.ts`): `src/lib/lidar/lazChunkTable.ts` decodes LAZ's chunk table, a port of LASzip (Apache-2.0, `NOTICE-LASZIP.md`), and laz-perf's `ChunkDecoder` decodes each chunk in a worker. Never read such a file with `arrayBuffer()` or laz-perf's whole-file `LASZip`: a LidarBC tile is up to 2.8 GB and 3–5 GB unpacked, past WebAssembly's 4 GB. Keep `lazChunkTable.ts`, `largeLaz.ts`, `largeLazDecode.ts` and `cropRegion.ts` free of DOM access; their tests run on laz-perf's Node build and a real LidarBC chunk table. A crop region (`cropRegion.ts`) is tested in the file's own CRS as each point is decoded; `pointCloudCrop.test.ts` pins that a chunked crop keeps exactly the points a whole-file crop keeps.

## Updating submodule data

1. Make and validate scraper/data changes inside `vendor/bcdatamapper`.
2. Commit and push the submodule change first.
3. Update the PGMaps submodule pointer without committing duplicate generated files under `public/data`.
4. Run `npm run data:sync-from-bcdatamapper` and the relevant tests/build from PGMaps.

Do not generalize this policy to app-owned files explicitly preserved by `scripts/sync-bcdatamapper-data.mjs`, or migrate other already-tracked datasets without reviewing their ownership and deployment path.

## Forestry tools

- `docs/forestry-tool-standard.md` lists what every `/dev/forestry` tool shares, the three tool shapes, and how a map keeps its own look through the toolkit. Read it before adding a tool or a map layer.
- Every map is the toolkit's `Map`. Give a tool its look through props (`styles`, `controls`, `MapTerrain`); do not call `map.addSource` or `map.addLayer` in a page. The doc lists the exceptions.

- `LidarMap.tsx` passes one style object as both `styles`. A second object, or `fallbackStyles`, lets the toolkit call `setStyle` on a theme change, which wipes every LiDAR layer: nothing re-adds them. A saved map image takes the point cloud in deck's `onAfterRender` (`pointCloudFrame`), because its canvas reads back blank at any other time and nothing reports it. Hillshade uses `MapTerrain reliefOnly`: maplibre-gl-lidar owns the map's 3D terrain, and a plain `MapTerrain` clears it.

## Forestry visual quality

- `docs/forestry-visual-quality.md` is the contract for `/dev/forestry/visual-quality`: what each reported percentage means, what the sightline model does and does not include, and the run's cost limits.
- Read its **Drive the view** section before touching `src/pages/dev-forestry/DriveCamera.tsx`. The eye-level camera depends on MapLibre behaviour that fails silently — an omitted `roll` argument reaches `jumpTo` as `undefined` and leaves the transform's projection matrices null from then on.
- Do not move the 3D stand onto a deck.gl overlay. Under this camera `map.transform.elevation` is a camera-fitting residual (about −294 m at Tabor Mountain), not the ground under the map centre, and deck.gl derives its camera height from it — so its camera lands at sea level while MapLibre's is on the hillside, and nothing draws with no error reported anywhere. `treeLayer.ts` takes MapLibre's own `modelViewProjectionMatrix` for that reason.
- The preview's eye and tree bases read the fixed DEM mosaic through `renderedGroundSource` (`@pgmaps/geo-toolkit/terrain`, re-exported by `src/lib/forestry/terrain/terrain.ts`), because MapLibre's renderer registers a DEM sample at its pixel corner and `ElevationGrid` at its centre; on steep ground the half-pixel put the camera into the drawn hillside. Keep the analysis on `ElevationGrid`'s own reading, and never fix eye clearance from `queryTerrainElevation`, which follows rendered LOD.
- Anything that needs the camera's ground position during a drive must take the viewing station, not `map.getCenter()`. Pitched at the horizon from eye level, the map centre is kilometres away on the skyline.
- The drive camera keeps the canvas size and the vertical field of view in the pose it compares (`driveController.ts`). MapLibre keeps zoom and centre through a resize or a lens change (*View options → Lens*, a field photo), so an eye-level camera that is not placed again after *Fullscreen* or a pane drag stands up to 29 m behind its station and draws the stems behind it in front, with nothing reported.
- MapLibre publishes no camera position — `getFreeCameraOptions` is Mapbox-only and `transform.cameraPosition` is internal. `treeLayer.ts` takes the view direction from the projection matrix's w-row gradient instead, which cannot disagree with the matrix that drew the ground.
- The tree silhouettes in `impostor.ts` are generated, not assets. Keep it that way: it is what makes the stand redrawable for a different species mix, and it keeps third-party vegetation assets and their licences out of the repo.
- The road view draws sixteen tree drawings (`TREE_DRAWING_IDS`, `forest.ts`): nine species, each conifer's young form and the tall shrub. A new species goes on the **end** of `TREE_SPECIES_IDS`: every drawing's seed is keyed to its place there, and the first six are pinned. A stem's `form` is read off its stand (`CANOPY_CLOSES_AT_METERS`, the thicket), never drawn from the stem's own random stream, which would move every later stem's height and crown. The scene package and final stand append the other three species after the original six (`PACKAGE_SPECIES_IDS`, `packageSpecies`). Preserve the first seven numeric tree fields; negotiate appended crown-base/DBH/expansion/form/source fields, stable string IDs and distant stand palettes through `sceneComponents.ts` before packing scenes or transferring final stands. Older engines receive six species and seven fields. See `docs/forestry-visual-tools-trial/stand-components-v1.md`. A species added to the drawings also needs its snag curve named (`borrowedBy`, `stand/snagDecay.ts`).
- *Baked from 3D* (`impostorBake.ts`, doc section **Baked tree cards**), the road view's default, takes each card from its own detailed mesh, eight views round the stem, on the CPU: keep it free of DOM access, never bake on the GPU (the bytes must be the same on every machine and in the tests), and never ship a tree model or texture to bake from. A stem shows **one** baked view through a dither, never a blend of two: a blend ghosts every branch and stops a stand's cover being the mean of its views', which is what `screenCoverage.test.ts` pins. A card and its mesh must stay the same tree: the same `bakedTreeMesh(drawing, variant)`, the same `stemTurn`, the same palette (`drawingPalette`) and the same light (`CROWN_LIGHT_GLSL`). The bake's across runs to the camera's left, as the layer's card corners do; `impostorBake.test.ts` pins it. What the method takes from three.ez's octahedral impostor (MIT) is in `src/pages/dev-forestry/NOTICE-OCTAHEDRAL-IMPOSTOR.md`; keep it in step. `detailedTreeMesh`'s `'solid'` build is the scene package's and must not change for the first six species; the road view draws the `'cards'` build (`treeSprays.ts`, DOM-free).
- The far bands (`isFarBand`, `forestPatches.ts`; doc section **The far forest**) draw more than a card a stem: a canopy tile over the stem's own ground, the light of the hill it stands on, and a run of card below its foot. All display only. A tile never lies over open ground: `canopyReachAt` (`placeTrees`) samples its whole square and stops it short of a clearing, a block, water or ground the inventory calls open, and `farForest.test.ts` pins that and that laying tiles moves no stem. Never read a stem's `canopy` or `slope` from its own random stream, and keep a tile's cut-out on the stand's crown closure through the sight line's slant (Beer–Lambert), never a fixed cover. The run below the foot (`FAR_CARD_SKIRT_METERS`) is there because MapLibre draws distant ground lower than the stems are stood on; it never raises a tree's top. Do not try to raise the terrain's detail with `setSourceTileLodParams`: at eye level the map's zoom is about 19, and (4, 12) asked the elevation source for some 4,500 tiles.
- `forestPatches` (`DevForestryVisuals.tsx`) is keyed to what places a stem and nothing else. Adding a look setting to `forestConfiguration` must not regrow the stand: if a new field changes where or what a stem is, add it to that key; if it only changes how one is drawn, leave it out.
- `GroundRelief` lifts the terrain component's own hillshade above the road view's ground fills by `moveLayer`; it adds no layer, and it stands down over imagery. Its place is by mount order (after the ground fills and after the block's own fill, which is what colours cut ground), so keep it there in `VisualQualityLayers`; it stands down in the note screenshot look and under the analysis colours, where ground is painted to be read flat.
- The trees' light (`ForestOverlay`'s `sun`) and their shadows (`shadows`, `treeShadows.ts`) are props read each frame, never part of `forestConfiguration`: a new configuration regrows the whole stand. Shadows are drawn before the trees and write no depth, so they cover no part of one. A stem the viewing gap leaves undrawn lays no shadow (`refreshShadows`). Tree layers share one compiled program of each kind and one spray sheet a map (`sharedResources`, `treeLayer.ts`), so a layer sets every uniform it reads on every draw.
- `screenCoverage.test.ts` pins how much of the view each drawing's far card and detailed mesh (`detailedTreeMesh`) covers, holds the mesh within 15% of its card, and holds its baked card within 3% of its drawn card (`BOUGH_CARD_SCALE` and `SOLID_SPRAY_SIZE` in `treeGeometry.ts` are solved to that: solve them again after changing a mesh, a silhouette or a spray picture). A drawn shape is screening evidence, not styling: the trial measured shape alone moving a stand's screening by 10–12 points. Change those figures only on purpose, saying why. Tree shading (`look: 'lit'`) and the atlas mipmaps (`atlasMips.ts`, coverage-preserving) must never change which pixels a tree covers.
- *Detail when stopped* replaces the near cards with meshes of the **same** stems (positions, heights, crown widths) only while the frame's matrix is unchanged for `DETAIL_SETTLE_MS`; never let it place stems of its own or stay on while the view moves.
- A stand's species come from its whole VRI record (`SPECIES_CD_1…6`/`SPECIES_PCT_1…6`, `speciesMixFromInventory`), and non-treed VRI ground grows no regional mix (`groundCoverFromBclcs`). Slash, edge rows and road scars (`harvestedGround.ts`) are display only; keep them out of every reported figure.
- Green-up height is area-weighted over slope classes, per the 1998 procedure's Step 5 — not `vegHeightForSlope(meanSlope)`. Table 6 is a step function, so the two disagree on mixed ground. `analysis.ts` accumulates it per sample; do not recompute it from `meanSlopePercent` in a panel.
- The planimetric denominator is the landform's **treed** area, per the 1998 procedure's "total green (forested) portion". It comes from VRI rank-1's `BCLCS_LEVEL_2`, live from DataBC's WFS (`bcVegetationInventory.ts`) — not the ArcGIS service, which carries only the VRI _Dead_ layer. Dividing by the whole landform reads the figure about 27% low at Tabor Mountain, enough to cross a class.
- In `bcVegetationInventory.ts` the bounding box goes in `CQL_FILTER`, never the WFS `bbox` parameter: WFS 2.0 with `EPSG:4326` is latitude-first, CQL's `BBOX` is longitude-first, and mixing them silently returns the wrong part of BC. Keep `propertyName` narrow too — the layer has 189 attributes and GeoServer will not generalise geometry.
- Never put `glyphs: ''` in a stubbed MapLibre style. The style then never finishes loading, `isLoaded` stays false, and every effect gated on it no-ops while the tests still pass — which hid 3D terrain and the 3D stand being switched off in the whole forestry e2e suite. Assert map state (`getTerrain()`, a layer id) rather than the sidebar text describing it.
- `vqo.ts` holds two threshold scales on purpose: perspective-view ranges define the objective, planimetric ranges are the timber-supply proxy, and they are not interchangeable. Judge a number against the scale it was measured on.
- Visual sensitivity units and EVQO are read live from DataBC's WFS (`queryVisualInventory`, `visualInventoryQuery.ts`, `REC_VISUAL_LANDSCAPE_INVENTORY`) everywhere on the page, *Find a landform* included, with no stored copy and no fallback: a failed read is an error with a retry, never an empty inventory. The reviewer's own *Keep inventory copies* (doc section **Keep inventory copies**) is the only exception, and is DataBC's full answer to the same request with its date, not a snapshot; every new BC inventory read on the page goes through `inventoryFetch`. Never read the ArcGIS `MapServer/6` layer (it stops at 10,000 of the 60,499 polygons) or reintroduce a snapshot built from it; a complete full-resolution copy is 200–270 MB gzipped and simplification distorts small units (13% area change at 1 m). Keep source coordinates intact. A nearest sensitivity unit is a review candidate, never an automatically verified visual landform.
- Tree placement tests every candidate stem against the clearings, and basemap water arrives as tile-sized multipolygons: test many points through `preparePolygons` (`visibility.ts`: parts with their own boxes, rings banded by latitude, exact `pointInPolygon` answers), never `pointInPolygon` in a loop. Before it, one patch took about 870 ms and the road view drew 1 frame a second (`preparedPolygons.test.ts` pins the equivalence).
- The page is a shared `TiledWorkspace` (`visualsWorkspace.ts`) with **two maps**: the plan map and the road view's own eye-level map, mounted only while the road view is open and on screen. The scene's layers are `VisualQualityLayers` with `mode="plan" | "eye"`; add a layer there once, choosing its map, never a `drive.active` switch in one shared map. `DriveCamera`, terrain, the tree stand, haze, the photo overlay and *Save viewpoint* / *Image* capture use the road view's map (`eyeMapRef`); the table bridge, legend and anything read from the basemap use the plan (`mapRef`). The plan's viewer marker is `MapViewerCone` fed by the pose's ground position, rounded so it is one `setData` a few times a second. The Viewpoint summary (`viewpointSummaryRows.ts`, DOM-free) reads the run and names every percentage's scale; never recompute a figure there. The e2e spec's `readMapState` reads a map by its pane (`visuals-road-view`, `visuals-plan-map`).
- The page's interfaces (Guided mode, Ribbon) are `public/visuals-layouts.json` over the shared kit (doc section **Guided mode and the Ribbon**): a command is one `visualsCommands.ts` entry, one `runCommand` case and one `commandStates` entry in `DevForestryVisuals.tsx`, never a hand-built header or ribbon button. The steps panel is rendered once and portalled into `editorHost`; the selected step is `useWorkflowPlacement`'s, shared by the sidebar's and the ribbon's tabs. The sidebar draws no title row: "Visual quality" is the header's heading (Guided mode) or the ribbon's File tab, one heading only. A plan-map tool the ribbon also offers runs the same handler (`lookFromRoad`, `startPlanDraw`, `toggleRoutePreview`).
- `MapSectionLayout` gives the page one fixed-height sidebar slot and that slot does not scroll, so everything the sidebar renders — `AssessmentPanel` included — belongs inside `MapSidebarShell`'s scroll container, which is what the step slot props on `Sidebar.tsx` (`setup`, `visit`, `landformScope`, `designReview`, `report`, …) are for. Stacked beside the shell instead, a panel pushes the shell's lower half and the bottom of its scroll port off the screen, where scrolling never reaches them; nothing overflows visibly to give it away.
- The sidebar follows the VIA handbook's five steps; the rating rules live in `via.ts` (see the doc's **The sidebar follows the VIA handbook's five steps**). The ocular class is always a reviewer input, Table 2 is read as printed rather than from the editable planning thresholds, and `viaReview` stays out of `sceneFingerprint` so editing a judgement never stales the run. Step 4 is made per group of views of interest (`viewGroups.ts`, `viaReview.stations` by the lead view's id; doc **Step 4 per group of views**): grouping is only ever suggested (`samePerspective`) and applied on the reviewer's click, a road keeps step 4 at the top of the review, and a step 4 made before groups is taken into a group only by *Use it here*. A view away from the run's station is rated on its own captured figure (`assessAtCapture`), never by inventing what only a run gives. The steps are tabs with every panel mounted but `hidden` when not selected, so an e2e test must bring a step forward (`showStep` in `forestry-visual-quality.spec.ts`) before touching its controls. A view of interest's open row is tabbed the same way (View, Record, Field, Report; `openViewRow(page, name, tab)`). Give each job one place in the sidebar — don't re-add a second draw/import/play control for something another section or the road-view panel already does.
- Step 2's field photo (`mapillary.ts`, `photoPose.ts`, `useFieldPhoto.ts`) needs only a Mapillary **client token**, `VITE_MAPILLARY_TOKEN` in the git-ignored `.env.local`; never add a client secret or commit a token. Mapillary poses follow OpenSfM (camera x right, y down, z forward; focal as a fraction of the longer side), and `orientationFromRotation` must keep reproducing the image's own `computed_compass_angle` — the unit test pins it to a real image. The Playwright web server sets a dummy token and the tests stub the Graph API.
- Any pitch the drive camera is handed goes through `horizonSafePitch` (`driveMath.ts`). A map pitch of exactly 90° — a lined-up photo looking level — crashes MapLibre's GPU process with 3D terrain on, and the page only shows "target crashed".
- A partial-cut block is not cleared ground: `analysis.ts` keeps it out of the proposal ledger and the screening canopy clearing, and `via.ts` adds its Table 6 equivalent to X only when the run sees it. Do not feed existing openings' `PERCENT_CLEARCUT` through Table 6 — it is not volume removed. The block's retention and partial-cut numbers stay out of `AnalysisInput`; only `harvestSystem` changes the run. The class pass paints a partial cut in its own class (`partialIn`/`partialOut`), outlined as a block but never counted as Proposed, and the sheet states its Table 6 figure beside the pixel figure.
- The drawn stand's density is calibrated, not styled: each crown's width comes from `crownWidthForClosure` so every distance band shows the stand's VRI crown closure (or `REGIONAL_STAND`). Do not reintroduce per-band width multipliers or species-constant crown widths — they closed the near stand to ~80% and left far hills at ~10% against a real 45–50%.

## Labs

- `/labs`, `/score-builder`, `/density-lab` and `/correlation-lab` share `ScoreBuilderSection`. Keep each lab to its own concept: a lab links back to the Labs page, never sideways. The Labs cards carry the last study area (`rememberLabStudyArea`), and `src`/`level` in a URL without weights outrank the starting example.
- GitHub Pages 301-redirects `/density-lab` to `/density-lab/`. Vite does not, so a path comparison that forgets the slash works locally and fails on every reload in production. Use `isOnLabPath`.
- A new `BoundarySource` needs a level in the reducer state, `getSelectedRegionLevel`, `setRegionLevel`, `parseBoundarySource` and the share state, or it falls through to the watershed level and throws.
- Region aggregation reads `PointGrid.near`, and `scoreRegionRows` hands the toolkit values already normalized by `normalizedRows`. The toolkit's percentile walks the whole value list for each value, which is regions² per metric on each of about 57 scoring passes, so do not route scoring back through it. Exports list only the metrics the view shows. Without this pair, large study areas freeze the page for minutes.
- `public/data/cimd/prince_george_cimd_2021.json` comes from `npm run cimd:sync -- <bc_scores_quintiles_EN.csv>`. StatCan publishes four dimensions as signed factor scores and no composite: dimensions are BC percentiles, and the composite is the user guide's summed-quintiles score. It is a PGMaps-derived figure, so say so where it is shown.
- Spatial autocorrelation (each lab's *Spatial pattern* section and *Clusters* map) is `spatialWeights.ts` (queen contiguity from the region polygons: a vertex within `DEFAULT_CONTIGUITY_TOLERANCE_METERS` of the other's boundary, so T-junctions count; islands and regions without a value leave the run and are named) and `spatialAutocorrelation.ts` (global Moran's I with Cliff–Ord normality and randomisation moments, local Moran's I by conditional permutation, Gi* with the region itself included, Benjamini–Hochberg). Both are written from the published methods and pinned to PySAL esda; keep them DOM-free. Permutations draw from the seeded `seededRandom`, so a map shows the same clusters every visit, and a draw equal to the observed statistic counts as extreme (`tieTolerance`). Run it through `useLabSpatialPattern`, only while the section is open or the map shows clusters, with the contiguity graph cached per region list; never inside the scoring passes. Whitebox's `getis_ord_gi_star` (whitebox-wasm 0.6.1) is not a reference: its variance is dimensionally wrong and clamps to zero, and its permutation runs reuse one RNG state. Every figure is PGMaps-derived and says so; exports carry the cluster columns only while the map shows clusters.

## Map layer loading

- `docs/map-layer-loading.md` is the contract for anything a map loads because of the view or a changing choice: nothing is removed because the camera moves, loading starts during the move, the superseded read is aborted, a swap is one frame, and a map that lags a choice says so. To add such a layer, or fix one that blanks, flickers or loads only after the map stops, read `.agents/skills/pgmaps-map-layer-loading/SKILL.md` and take the first pattern in the guide's table that fits (tiles, hand-off, `moveLayer`, view window, blocks) before writing a loader of its own.
- A layer ships only after `scripts/map-loading/measure.mjs` has run on it in a real browser, before and after, with its page's setup in `scripts/map-loading/setups/`: the run fails when the layer was missing on any frame or the whole view went empty during a gesture. Its figures go in the guide's **What was measured**, and anything found and left goes in **Not built**. Never pass `visible: … && !moving` to a reader, return `null` while the next picture is read, or remount a tile layer with a `key`: those three are what the November 2026 trace found.
- The generic pieces (the view window, the hand-off, tile and hillshade layers that follow `beforeId` and `tiles`, the image layer that takes pixels, `exposeMapTransform`) are toolkit code: change them in the `ahzs645/geo-toolkit` repository first, then move the pointer. The guide's **Where this lives** lists each with its PGMaps entry point. The canopy tile reader, `MapCategoricalRaster` and the measuring script stay here.

## Photo matching

- To line a field or aircraft photo up with the terrain, check it against the map, or draw proposed blocks and roads into it, read `.agents/skills/pgmaps-photo-matching/SKILL.md`. The bench is `scripts/forestry/photo-matching/`; the method and its measured accuracy are in `docs/research/landscape-photo-matching-2026-11-14.md`.
- A matched camera reaches `/dev/forestry/visual-quality` through the own photo's window (Camera → *Adjust* → *Use a matched camera…*), which reads the bench's case file in the browser (`matchedCamera.ts`) and adds a row to the options card. An own photo with `altitudeMeters` stands its eye at that altitude; keep its height over the road view's ground derived (`eyeHeightOver`), never stored.
- Own photos are lined up in one window (`OwnPhotoDialog.tsx`, three tabs: Photos, Camera, Use, the hand tools behind Camera's *Adjust*; doc section **A photo of your own**), and the sidebar keeps only a summary (`OwnFieldPhoto.tsx`): put a new own-photo control in its tab of the window, never back in the sidebar. The set, the automatic queue, the window's open state and tab, and everything they work on live in `useFieldPhoto` (pure rules in `photoQueue.ts`): the window hides itself while the plan answers a pick (`steppedAside`, with the banner's hint passed to `onPickPoint`), and `DialogShell` unmounts its content while hidden. The queue never accepts a camera and never overwrites a pose the reviewer set (`queueMaySetPose`). Step states come from `ownPhotoSteps.ts` (DOM-free): a done step says what the camera rests on, never that it is right, and the phone's own heading is never done. The skyline over the photo is drawn from the camera tools' terrain for the camera as it stands; keep it following the pose, not a tool's result.
- The own-photo queue's speed rests on four things; keep them. The model view is coloured from the hit buffer (`colourHits`, `photoViews.ts`), never a ray cast per pixel: per pixel one 320-pixel view took several seconds and was most of the queue's 152 s for fourteen photos (about 30 s now), and `photoViews.test.ts` pins the two pictures together. The features check is read after the searches (`featuresNext`, `photoQueue.ts`: the open photo first, the others once no search waits), never inside `runPhoto`; a read that fails must end *failed*, never unread, or it is tried again without end. Photos are read side by side (`inLanes`, `heicDecodeConcurrency`) and each joins the set as it is read; never go back to reading the whole set before showing any. HEIC decodes go through `heicDecodePool.ts` (DOM-free, the worker passed in), never a worker made per photo. A strip of photos shows `thumb`, never `src`: a 24-megapixel picture is decoded whole for each thumbnail.
- *Match flight photos* pairs two photos with the matcher the reviewer chooses (`photoMatchers.ts`): XFeat, bundled, or the trial ALIKED + LightGlue pair, whose 48 MB of models are never committed or bundled: `npm run photo-match:fetch-models` puts them in the git-ignored `public/models/photo-match/`, checked against `photoMatchModels.json`, and the worker reads them whole and refuses a file of the wrong size (a site without them answers with its own page). They are WebSfM's exports (`NOTICE-PHOTO-MATCH-MODELS.md`); a GitHub release cannot serve them to a browser. Do not deploy them or make the learned matcher the default without the owner's word: its evidence is two pairs of one flight. In `photoRelativePose.ts` a matched point with no parallax takes no side for a motion (`sidesOf`): never go back to counting it as behind the camera, which refused every pair matched mostly on distant ground. Keep the GPS direction check as it is: it is what refused to carry a wrong accepted camera to its neighbour. Keep `photoMatchers.ts` free of DOM and network access.
- The own-photo window never takes something away to put it back (doc **A photo of your own**, *Nothing is taken away to be put back*, *Views drawn ahead*). Keep these: the queue starts its next photo in a layout effect; the open photo's terrain is held while it is open (`heldOwnTerrain`), whatever the two-entry cache does; while a camera's ground is cast the last drawing stays up faded (`held`, `PhotoWithOverlays.tsx`) and is never read against; the picture's box is sized from the photo's own shape (`fitBox`), never from a loaded image. Every options row's model view is drawn ahead (`optionViews`), and they record no check; the open photo's option cameras are cast ahead into `optionHits`, apart from `hits`, which the rest of the set fills and empties. A new thing drawn for a camera goes in the worker (`photoWork.ts`: the comparison's `cameraCues` job, the layers' `overlay` job), never on the page's thread at each click. Layers on the photo are laid through `usePhotoLaidLayers.ts`, kept by camera and by what a layer holds (`layerSignature`), never by the feature list's identity, which changes with every camera; they are laid ahead for the option cameras, and a camera waiting for some of its layers draws none of them. What the comparison of cameras offers (*Start from it*, *Compare with depth*) sits under the options card, because it arrives after a photo opens. The depth worker is kept between photos (`photoDepth.ts`) and let go when idle; never start one per photo. The Camera tab's photo and its comparison with the model view (overlaid or *Side by side*, two pictures sharing one view) are whole in view and zoomed with the shared `ZoomPan` (`docs/shared-ui.md`, **Zoom and pan**): a mark that keeps its size reads `--zoom-pan-scale`, and the swipe's divider is moved by its own handle while enlarged. There is no spec for this window: check a change to it with a frame-by-frame run (`tmp/`-style throwaway script, real GPU; see the doc's figures).
- A photo's skyline is read by each of `SKYLINE_READERS` (`skylineFit.ts`: the colour reader, then three brightness readers for a sky lit from behind or hazy) and the best fit kept (`searchRank`); never go back to the colour reader alone, which read 0 columns on a sunset frame and still named a best heading. A best fit with fewer than `MIN_SKYLINE_COLUMNS` agreeing columns is *no skyline*. For a photo the skyline does not settle the queue compares cameras by the ground after the searches (`compareUnsettled`), and uses depth only where this browser already holds the model (`depthModelStored`): never start a model download the reviewer did not click for. A depth estimate is kept by record and model (`photoDepthFor`, `toolsStorage.ts`), never estimated twice. What the comparison favours is a start offered beside the options, never the photo's camera.
- A read skyline is searched only when it has sky above it (`believableSkyline`, `skylineFit.ts`: the side above clearly brighter or clearly smoother than the side below). Never search a line that fails it: on a frame of forest with no sky every reader found a shadow's edge, and the search named a rolled camera as best fit with 74% of its columns agreeing. `SKY_BRIGHTER` and `SKY_SMOOTHER` are measured on one flight; move them only with more frames, and the doc's figures with them. A photo with no believable skyline is compared by the ground like an unsettled one. When the cameras that fit about as well as the best look in directions far apart (`undecidedHeadings`, `photoCombined.ts`), the window names the arc and offers no camera to start from: never present the top of a tie as a suggestion. The phone's tilt is a start, never proof: the same frame read level at exactly 1 g while showing no sky where a level camera must.

- Layers over a photo are listed by the shared `LayerList` (`src/components/ui/layer-list.tsx`); a new thing to show on a photo is a `PhotoCustomLayer` (`photoLayers.ts`, as `scenePhotoLayers` adds the road to assess), never a new built-in layer id unless the photo tools must read or pick it themselves.
