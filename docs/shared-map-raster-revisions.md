# Reviewed raster revisions

`scripts/shared-maps-worker/publish_raster_revisions.py` publishes two narrowly
defined repairs to an existing collection: a bounded transparency mask in the
current native grid, or a finer raster exported from a recovered, frozen source
model. It preserves the map's exact native extent and CRS, all stored geographic
bounds, original-scan variants, sources, saved projects, confidence, and prior
alignment-review evidence. It does not fit controls or certify ground accuracy.

Keep real collection URLs, catalogues, source files and review evidence outside
the public repository, as described in `shared-map-viewer.md`.

## Prepare and review

Build the new GeoTIFF, PMTiles and WebP thumbnail before publishing. Use
`build_catalog.py`'s `create_tiles` and `thumbnail` functions; the tile builder
compares every packaged tile with its generated bytes. Retain the preceding
native raster and the inputs needed to reproduce the repair.

For a mask, retain a binary PNG in the native pixel frame. The validator checks
every RGB value, every alpha value outside the mask, and the exact alpha result
inside it. The mask is limited to five percent of the frame. The full source
sheet remains available for reading the excluded page content.

For a source-resolution rebuild, retain the exact original image, frozen model,
and rebuild recipe with hashes. Establish the source-to-working-image frame
before composing it with the existing model. Replay the previous output and
check all fitted and withheld predictions. Use an integer subdivision (2–16)
of the old grid with the same outer extent; record how the display sampling
compares with native scan detail. This scientific evidence requires review:
the publication validator checks the hashed inputs and frames but does not
execute arbitrary recipes or prove a model's ground accuracy.

## Private stage

Use schema `pgmaps-raster-revision-publication-v1`, with these fields:

| Field                               | Content                                                            |
| ----------------------------------- | ------------------------------------------------------------------ |
| `collectionBase`                    | Existing capability-scoped collection base URL                     |
| `beforeCatalogue`, `afterCatalogue` | Relative paths to exact catalogue snapshots                        |
| `beforeSha256`, `afterSha256`       | SHA-256 values of those snapshots                                  |
| `revisions`                         | One to eight explicit raster revisions                             |
| `textUpdates`                       | Optional bounded `group`, `id`, `field`, `before`, `after` changes |

Each revision names an existing native record through `itemId`, uses `kind`
`alpha-mask` or `source-resolution`, and supplies `beforeRaster`, `raster`,
`tiles`, `thumbnail`, and `evidence` references. Each reference has a relative
`path` and exact `sha256`; the three deliverable references also have `bytes`.
All paths resolve inside the stage directory. The revision also supplies a
plain-language `note`, exact `records` in catalogue order (`group` and `id`),
and `tileMetadata` (`minZoom`, `maxZoom`, `tileCount`, `width`, `format`).

A mask additionally supplies `mask`. A source-resolution rebuild supplies
`sourceImage`, `frozenModel` and `rebuildRecipe`. The prepared PMTiles header
must agree with the claimed tile count, zooms, format and geographic bounds.
Validation regenerates the delivery products from the repaired raster and
compares every tile coordinate and payload plus the thumbnail bytes. This
prevents an old display archive from being paired with a new native raster.
Use the same preparation/validation toolchain; GDAL, rasterio, Pillow, NumPy,
httpx and PMTiles are required. Temporary regeneration files are removed.

Use `revised_catalogue(stage_directory, stage, before)` to construct the proposed
catalogue, inspect its complete diff, then pin its hash. The constructor updates
every native/curated alias of the old raster, retains alias-specific labels,
and records the preceding download, tiles and thumbnail under `rasterRevision`.
It adjusts native-raster storage totals once per native record. Old objects are
not deleted. The validator reconstructs the allowed result and rejects all
extra changes. Text updates allow only existing titles, date labels,
descriptions and caveats; their exact prior values must match.

Earlier alignment-review entries retain their date and evidence. Add a clear
revision note when those earlier comparisons predate the served raster. A
finer output does not make an inherited fit more accurate.

## Validate and publish

```sh
python scripts/shared-maps-worker/publish_raster_revisions.py \
  --stage /private/revision/stage.json
```

This is a read-only check and needs no owner credentials. After reviewing the
assets, evidence and catalogue diff, enable the existing temporary owner upload
secret and publish with owner-readable settings:

```sh
python scripts/shared-maps-worker/publish_raster_revisions.py \
  --stage /private/revision/stage.json \
  --owner-config-file /private/owner-settings.json \
  --receipt /private/revision/publication-receipt.json --apply
```

Both image and raster publishers use the same conditional transport. It checks
the live catalogue hash, verifies immutable uploads and archive ranges, requires
a strong current ETag for activation, and checks the final catalogue bytes.
Remove the temporary owner secret after publication, then independently read
back the new objects. A concurrent catalogue change requires restaging; do not
force an overwrite. Receipts cannot overwrite the stage, catalogues, evidence,
source inputs, prepared objects, or owner settings.

## Focused checks

```sh
python -m unittest discover -s scripts/shared-maps-worker -p 'test_publish*.py'
```

The raster cases cover alias propagation, preservation of original images and
prior reviews, exact masks, frame changes, input tampering, PMTiles metadata,
source-resolution subdivisions, and bounded text edits. Image-publisher tests
continue to exercise conditional activation, stale live catalogues, immutable
object mismatches, receipt paths and repeated publication.
